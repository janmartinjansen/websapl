Sapl → WebAssembly

The same program on the JMVM interpreter and as native WebAssembly (twice), compiled in your browser

← WebSapl home

Press Run and the program is compiled three times, entirely in this tab. On the left it becomes JMVM bytecode for the interpreter. In the other two columns the same Stage-4 Retag goes through retag2wasm, a code generator written in Sapl that emits a WebAssembly module directly: no C compiler, no Binaryen, no server. The browser then compiles that module to machine code. The middle column uses the browser's call stack (fastest, but deep programs run out of it); the right column keeps its own stack in memory, like the JMVM (always fits, at a price that differs a lot between browsers).

Good to know

      
    
        
  • Run times are the best of three runs on each side (the first run of fresh code is slower); compile times
          are listed separately. The JMVM time is the VM's own measurement of the program, without loading.
    • 
        
  • The JMVM keeps its own stack in memory. The middle column uses the browser's call stack, which is small
          (about 1 MB on a Mac, less on an iPad; the module therefore runs in the page, not in a worker, and the
          page does not respond while it runs); very deep programs such as sort and twice
          stop there with a message.
    • 
        
  • The right column turns every call that is not a tail call into a continuation on its own stack (2 million
          cells) and returns through it, so the browser's stack never grows. That always fits, but costs something:
          little in Chrome, more in Firefox, and in Safari it can be slower than the JMVM itself.
    • 
        
  • Not yet supported by retag2wasm: try/catch and floating-point
          literals. The JMVM column runs them as usual.
    • 
        
  • More background: the WebAssembly backends factsheet.
