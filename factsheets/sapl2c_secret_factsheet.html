Performance Analysis • Where the speed of sapl2c comes from

What Is the Secret Behind sapl2c’s Performance?

A compiler of about 2,000 lines keeps up with GHC -O2 and beats Clean native. Is that down to the Retag format, to the quality of clang, or to something else? The short answer: there is no single secret. Three factors multiply, and the Retag format is the hinge between them.

1. Retag Unlocks clang; clang Does the Machine Work

The engine: clang/LLVM for free

Register allocation, instruction selection, branch layout and scheduling come from LLVM at no cost. GHC and Clean each maintain their own native backend for that work, built and tuned over decades; Clean’s code generator stems from an earlier processor era. (Note: it is clang, not gcc, though that matters little for the argument.)

The key: whole functions, named locals

clang can only help when it sees whole functions with named variables and explicit case trees. Retag gives exactly that. The jmvm2c experiment is the control: the same clang, fed from bytecode where values live on the VM stack, gave 9.3 MB of C, a 47 s build and a 442 ms self-compile. From Retag: 2.9 MB, 4.1 s, 248 ms.

You cannot credit the win to clang or to the format in isolation. Retag is the key; clang is the engine.

2. Memory: Allocation Is Most of the Work

Lazy functional programs are, above all, allocation programs. The largest single-measure gains did not come from code generation but from the memory path:

  • a growing Cheney nursery that starts at 8 MB and stays in cache: sprimes −45%, match/prolog −21%, hamming −18%;
  • allocation is just hp += N, with straight-line allocations merged into a single HEAPFULL(N) check;
  • shadow-stack saves only on the slow GC path, and none at all where a local is proven to be a non-pointer.

Whoever gets the memory path right has already won most of the race.

3. Sapl Is Already Close to the Machine

This is arguably the real “secret”. After gen1, a Sapl program is first-order (lambda-lifted), carries explicit strictness (!, inferred or annotated), has CAFs made explicit (=:) and uses one uniform value representation. There is very little abstraction left to compile away.

What GHC’s heavy machinery is for

Type classes and dictionaries, polymorphism and specialisation, monads, list fusion, worker/wrapper and unboxing driven by static types. That is where most of GHC’s optimiser earns its keep.

What the benchmarks exercise

First-order recursion, pattern matching, laziness and lots of small allocations. On that terrain the machinery above has little to remove, so a compiler without it does not fall behind.

Two Supporting Factors

Modern hardware is forgiving

An Apple M4, with strong branch prediction and out-of-order execution, makes the untyped runtime tag checks nearly free: fib needs only one tag test per operation and has zero shadow-stack spills.

“Few resources” means few lines, not little knowledge

The design choices (the {v, hp} two-register return, the uniform MUSTTAIL ABI, the non-pointer analysis, the nursery sizing) rest on years of experience with Clean and Sapl, and on careful measurement: hardware counters and interleaved A/B runs.

The remaining gap is therefore mainly a matter of types (untagged integers, no runtime tag checks), not of compiler quality. That is where the next gains lie, if one wants them.

In one sentence: Retag makes clang usable, the nursery makes memory fast, and Sapl leaves little to optimise away.
