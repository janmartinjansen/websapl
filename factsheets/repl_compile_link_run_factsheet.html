REPL in Sapl · dynamic compilation

Inside the REPL: Compile, Link, Run

The Sapl REPL is one running Sapl program that contains its own compiler and linker. Every line you type becomes a small piece of bytecode. The REPL links that piece against the session in Sapl, places it behind the code that is already running, and jumps into it. Nothing is restarted and nothing is recompiled that did not change. Every listing below comes from a real session.

1 program
preprocessor, compiler (gen1), typechecker and linker as modules of the REPL itself
~1–4 ms
per line after the first: compile, link, install and run*
Append-only
new code always goes behind the old; old code is never changed or freed
5 calls into C
four @meta: queries and one @install:; all linking policy is Sapl

1. A program that compiles into itself

The REPL is repl_sapl/mini_repl.spp, built into repl_sapl/build/mini_repl.jvb. It imports the preprocessor (PP), the module compiler from gen1 (SM), the typechecker (TC) and the linker laadformaat/link.cfp (LK) as ordinary Sapl modules. It also contains a small prelude (showing values, strings, lists) that every compiled line may call.

The same .jvb runs everywhere: in a terminal with ./rs-driver, behind the REPL tab of the Workbench, and inside the WebSapl Web Worker on the wasm VM. Between lines the program waits in readLine. In the browser the VM saves its registers there and returns to JavaScript. The next line resumes it at exactly that point. The heap, with the session and all values computed so far, stays where it is.

2. The life of one line

Take the line cube 3, typed after :def sq x = x * x and :def cube x = x * sq x. It is the session's second expression, so it becomes res1. Its unit number is 3, because every line gets a fresh number and the numbers never go back. These are the stages, with the real intermediate files from the session's working directory (mr_u3.*).

1Wrap the line as a unit

An expression becomes a CAF resN =: line, so its value is computed once and stays in the session. A function __goN shows it. The REPL calls the typechecker on the line first and writes the type it finds ("Num") into the call, so lists, booleans and records are shown correctly. it is replaced by the previous resN as text: it * 10 became res5 =: res4 * 10.

mr_u3.cfp — the unit
res1 =: cube 3
start = __go3
__go3 nbTbl nbCur = printValX nbTbl nbCur "Num" res1

A :def becomes the definition plus start = 0. A line that uses an imported alias also gets an import extern line, which tells the preprocessor the module's names without including its code again:

mr_u9.cfp — after :import "lib/list.spp" as L
import extern "lib/list.spp" as L
res3 =: L.sum (L.map cube [1, 2, 3])
start = __go9
__go9 nbTbl nbCur = printValX nbTbl nbCur "Num" res3

2Preprocess (Sapl+ → Sapl)

The preprocessor resolves L. to the module's real names. It also turns list literals into constructors and renames parameters with a tag computed from the unit's text. The tag comes from the text, not the unit number, so the same definition has the same helper names in every session. That matters when saved values are restored later.

mr_u9.pp.cfp
res3 =: list__sum (list__map cube (Cons 1 (Cons 2 (Cons 3 Nil))))
start = __go9
__go9 __pat_r1077639575_0 __pat_r1077639575_1 = printValX __pat_r1077639575_0 ...

3Compile against the session's interface

gen1's module compiler (smCompile) compiles the unit by itself. It does not see the code of the rest of the session, only an interface: for each function the name, arity and strictness (the .defs.txt lines), and the ADT declarations. To keep this cheap, the REPL passes only the external names that the unit actually mentions. Here that is cube 1 1 and printValX 4 0000, not the whole prelude or every function of every import.

The result is a chunk: bytes in the .jvb format, kept as a value in memory. Below is the text form of the same chunk (from saplcomp_module, stage jmvm). The first line is the label table. Labels 6–9 (printValX, cube) are not defined in the chunk; they are open names. In the bytes they are negative label numbers.

4Link, in Sapl

LK.lkLink img bytes takes the session image (LkImg, a Sapl value) and the chunk. It asks the VM four things: where the code ends (@meta:codeend), how many strings, CAFs and type-ids are in use (@meta:nstrings, @meta:ncafs, @meta:nexttid). Then it rewrites every operand by its kind, which it takes from the instruction table (vm/instructies.tab):

  • own code address: plus the base (the chunk goes right behind the current code);
  • open name: the address of the latest version of that name in LkImg (strict or lazy entry, by the _lazy suffix); an unknown name is an error;
  • string: a new global string number;
  • type-id: the session's id for that ADT. A type with the same name and the same constructors keeps its id; anything else gets a new one;
  • CAF: a slot in the VM's CAF table. The chunk's own CAFs get fresh slots, and a CAF of an earlier entry gets the slot it already has.

The linker appends a new entry point: the CAF set-up of the chunk (now with its real slots), then tailcall start. It writes the result as a .jvb with a LINK section (base, entry, number of strings before it), and computes the new LkImg.

5Install, in C

lookup "@install:<bytes>" runs installLinked (vm/laden.h). It decides nothing. It checks that the base is the current end of the code and that the string count matches (otherwise the session is stale). It checks that every call target lies inside the code and that no type-id is taken by another type. Then it copies the words behind the code, adds the strings, functions and types to the VM's tables (for showing values and for diagnosis), runs makeCode on the new part only (opcodes to dispatch addresses, superinstructions), and returns the entry address as a function value.

6Run, then seal

applyDynamic calls the entry. It fills CAF slot 99 with a thunk for cube 3 and tail-calls start, which returns __go3. The REPL applies that to two tables for the display (import aliases and current names), and __go3 forces res1 and prints 27. Only after a successful run does the REPL make the new LkImg the session's image (lkSeal) and add a res1 entry to the session.

The whole step in code (runChunkI in mini_repl.spp):
let !r = LK.lkLink img bytes in applyDynamic (lookup ("@install:" ++ LK.lkLinked r)) Nil <#> LK.lkSeal (LK.lkNewImg r)

3. What the session remembers

The entries (St)

A list, in session order. Each entry has its name, its source text, its kind, the bytes of its chunk, its interface (.defs, ADT lines) and, for imports, the parsed modules for the preprocessor and the typechecker.

0 / 1function / CAF (:def)
2ADT (:def ::Shape = ...)
3resN (an expression line)
4 / 8module code (hidden) / import alias
5notebook cell group (:nb)

It also keeps a counter for unit numbers, the next resN, the previous state (for :undo), the type schemes, and the interactive notebook cells.

The image (LkImg)

What the linker needs, as a Sapl value:

  • funcs: name → every address ever loaded for it, oldest first (two per version: strict, lazy);
  • types: every loaded ADT with its id and constructors;
  • cafs: name → CAF slot;
  • nextTid, nextCaf.

At start-up it is built from the prelude's interface, with addresses from @meta:faddrs:<name> (about 70 names, not the thousands of functions in the REPL itself).

4. Redefining a function: who must be recompiled?

Linking turns names into absolute addresses. So a chunk that is already in the code calls the version of a name that was current when it was linked, and keeps calling it. That makes redefinition explicit: when sq changes, every entry that uses sq, directly or through other entries, must be compiled and linked again so that it points to the new code.

dependentsOf finds those entries. It starts from the changed name and repeatedly adds every function or CAF entry whose source text mentions a name already in the set. For an ADT the constructors count too, both the old and the new ones: whoever uses Rect depends on ::Shape. The REPL first compiles all of them and only then links them, in session order. If one fails, nothing is loaded. Expression results (resN) are not recompiled: they are snapshots.

From then on, names resolve to the old addresses again. The first :undo removed res2 and the second removed the new sq, so the next cube 3 linked to the original cube at 342765, which still calls the original sq.

5. Types, CAFs, strings and imports

ADTs

:def ::Shape = Circle r | Rect w h gave Shape the new type-id 284 when its chunk was linked. A later chunk that mentions Shape maps its own local type-id to 284. Redefine Shape with other constructors and the linker gives it a new id. Old values keep the old one, and the definitions that use the constructors are recompiled (section 4).

CAFs and results

Each resN is a CAF with its own slot: res0 got 98, res1 99, res2 100. After :undo the new res2 got slot 101, a fresh one, so the old value was untouched. A CAF is evaluated at most once. Later lines that use it read the same slot.

Strings

Each chunk brings its own string literals. The "Num" of four consecutive expressions became strings 4912, 4913, 4914 and 4915. Nothing is shared between chunks, which keeps linking simple.

Imports

:import "lib/list.spp" as L loads the module's code once per path, as a hidden entry, plus an alias entry. For the standard libraries the chunk is prebuilt: repl_sapl/build/modules/index.txt lists each with the length and a hash of its source. If they match, the REPL links the prebuilt .jvb (here 2,410 words); otherwise it compiles the module on the spot. Either way the chunk goes through the same lkLink.

6. When a line fails

Compile error

repl> :def bad x = x + y
fout: saplcomp: onbekende naam y in functie bad ...

The compiler raises the error inside a try. No chunk is linked and nothing is loaded. The session is exactly as before; only the unit counter moved on.

Runtime error

repl> L.nth 5 [1, 2]
fout: List.nth: index te groot

This chunk was linked and installed (load 15, base 345699, CAF slot 105), and then the run threw. Because lkSeal comes after the run, the session keeps its old LkImg and the resN counter does not move. The code array and the VM's counters did move. That is why lkLink always takes the maximum of its own counters and the VM's @meta: values.

error and VM faults inside a line are catchable in the same way (syscall 8, vmFault), so the REPL prints fout: and waits for the next line.

7. What is Sapl and what is C

ConcernWhere
Parsing, preprocessing, type inference, code generationSapl (PP, TC, SM)
Which entries to recompile; order of loading; :undoSapl (mini_repl.spp)
Name → address (latest version), relocation, type-ids by name + constructors, CAF slots, string numbers, entry pointSapl (link.cfp, ~590 lines)
End of code, string/CAF/type counts, prelude addressesC: lookup "@meta:..."
Sanity checks, copy, makeCode, return the entryC: lookup "@install:..." (installLinked, ~80 lines)

This split keeps the VM small: the same installLinked serves the native VM and the wasm VM. Changing how linking works is a change to a Sapl module, rebuilt with the REPL. Until 11 October 2026 the linking policy lived in C. It was moved to Sapl and the C loader was deleted.

The price of append-only. Code, strings and type-ids are never freed, not even by :reset (which only empties the session and the image). The code array has room for the program plus 4,000,000 words. An expression costs about 58 words and a small definition about 24, so a session can load tens of thousands of lines; when the array is full, @install stops with the error code-array vol.

9. How notebooks use this, and why they need it

The notebook is not a separate system. It is one more REPL command, :nb <file>, in the same running program (see The Notebook Wire Protocol for the messages).

  • Definition cells are grouped into units (cells that use each other form one unit). Each unit goes through exactly the steps above, compileUnitB then runChunkI, and becomes an entry of kind 5.
  • A unit whose text is unchanged, and that uses nothing that changed, is not compiled or linked again. A changed name propagates to the units that mention it, just like dependentsOf for :def.
  • The expression cells of one run are compiled together as one chunk and run with runChunkV. It is linked against the image but not added to it: the expressions are output, not definitions.
Why this is essential for the notebook.
  • Speed. Editing one cell compiles and links one small chunk instead of the whole notebook. In the sieve example, a first run takes 124 ms and editing n afterwards takes 7 ms.
  • Values survive. The VM never restarts, so evaluated CAFs stay in the heap. The sieve's primes keeps every prime it has already found. A whole-program recompile would restart the program and compute them all again.
  • Live cells keep working. An interactive cell is a function value, a stepper, held in the session. Because code is append-only, the addresses inside that value stay valid while other cells are recompiled, so its token keeps answering events.
  • It all runs in the browser. Compiler, typechecker and linker are Sapl bytecode in the same wasm VM. There is no server and no native toolchain, and the VM itself only needs the small @install primitive.
