The Toolchain Is the Program

Most comparisons between functional language implementations stop at speed. This factsheet looks at a different axis: how easily the language can be used, and how easily its toolchain can be built into an application, a browser page or a notebook. In the JMVM the only C is one small virtual machine. The compiler, linker, typechecker and REPL are bytecode that runs on it, wherever it runs.

1. Judged on speed alone, native Clean wins

A factor of two to three is the price of the JMVM. The question is what it buys.

Clean, native ARM64
107 ms · 1.0×
Clean ABC interpreter (abci)
235 ms · 2.2×
JMVM, with superinstructions
356 ms · 3.3×

Geometric mean over 14 programs (12 core benchmarks, eval2, gen1), Apple M4, best of 7 runs. Own measurements, from experiments/clean_vergelijking.

Allocation-heavy code

On programs dominated by allocation, such as twice, the gap is small: 1.4× for the JMVM, and about equal for abci.

Strict integer recursion

On fib, knights and eval, native Clean keeps numbers in registers and is six to ten times faster than the JMVM.

2. Where the C lives

What each toolchain is made of, and in which language each part is written.

Clean 5.1

Frontend and typecheckerClean · about 77,000 lines
ABC generator and strictness analysisC · about 47,000 lines
Native code generator (cg)C · one backend per platform
Runtime and garbage collectorC and assembly · per platform
LinkerThe system's linker

JMVM

Preprocessor and typecheckerSapl · about 11,000 lines
Compiler (gen1, self-hosting)Sapl · about 11,000 lines
LinkerSapl · 589 lines
REPL and notebook kernelSapl
VMC++ · about 12,000 lines · one source, native and wasm

Blue: written in the language itself. Orange: C, or specific to a platform. Grey: the system's own tools.

Clean's frontend has been written in Clean since Clean 2.0, but code generation stayed in C: the ABC generator, and below it a native code generator and runtime for every platform. In the JMVM the only C is the VM. Everything above it is Sapl, compiled by itself.

4. Compiling is just a function call

An application embeds the VM and loads the toolchain as ordinary bytecode.

one JMVM process (C)
Step 1
Your code
A cell, for example cell.spp
Step 2
Preprocess + typecheck
Sapl, loaded from a .jvb file
Step 3
Compile (gen1)
Sapl, loaded from a .jvb file
Step 4
Link
Sapl, loaded from a .jvb file
Step 5
Run
The same VM

What this means

  • Users write code; the application compiles, links and runs it in the same process.
  • No C compiler, no system linker, no step that depends on the platform.
  • Every step except the VM itself is a Sapl program loaded from a .jvb file.

The same holds in a browser tab

WebSapl compiles in a web worker. That is also why the REPL, the notebook and the Workbench need nothing installed beyond the VM.

📓

5. Notebooks and interactive documents come free

The notebook kernel is the REPL, and the REPL is just a Sapl program.

Cells compile in the page

Each cell goes through the same preprocessor, typechecker and compiler, in a browser worker. No server needed.

Live and interactive

Cells that react to input, plots, graphics and CSV data from Sapl libraries. Values survive between sessions.

One notebook, two engines

In WebSapl on wasm, or in the Workbench with a native process and real files. Heavy work can move to a server.

Nothing in the notebook was built as a separate product. It is the REPL in notebook mode, running the same compiler that builds everything else. Interactive cells, saved values and the server compute process are all Sapl on top of that. See also the notebooks factsheet.

6. One VM on both sides of the wire

Moving code and data between a server and a client.

Clean: lazy interworking

Native code on the server, the ABC interpreter in the client. Graphs, unevaluated parts included, move between them, and missing code is fetched when needed. Elegant, and rare among languages.

The price: two representations, and a bridge between them.

JMVM: nothing to translate

The same VM, bytecode and heap layout on the server (native) and in the client (wasm).

Already there: .jvb code units, a linker in Sapl, and saving and restoring values.

Still to build

send unevaluated thunks fetch missing code by hash typed unpacking
Context. Clean's approach is described in "Lazy interworking of compiled and interpreted code for sandboxing and distributed systems" (Staps, van Groningen, Plasmeijer, IFL 2019). Other languages share code at build time and send only data (JavaScript with Node), need the same module loaded on both ends (Erlang), or only send static closures between identical binaries (Cloud Haskell). Unison comes closest, with code addressed by hash, but it is strict.

7. What it costs

An honest comparison has to name these.

AreaWhere we stand
SpeedTwo to three times slower than native Clean, and it will stay that way.
TypesSapl's typechecker only warns. Haskell lite still has gaps (Foldable, infixl).
EcosystemFew libraries, little documentation outside this repository, few users.
PitfallsSome mistakes in Sapl still compile silently, such as == on strings.
Speed matters for heavy computation. For the applications we have in mind, such as command and control, notebooks and teaching, the time goes into people and the network, not arithmetic.
Conclusion: port the VM once, and everything else comes along. The toolchain, the REPL, the notebooks, and the languages on top: Sapl, Sapl+, Haskell lite, MicroHs, and Clean through ABC. A new platform needs a C++ compiler for the VM, and nothing else. That is the advantage Clean's ABC interpreter aims for too, but there the compiler itself still contains C.
