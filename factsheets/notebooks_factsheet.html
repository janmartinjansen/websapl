1. The Notebook Paradigm Shift: Curing Mutable Hidden State

How functional purity and call-by-need laziness eliminate the fundamental flaws of Jupyter and Python.

The Pain Point: The "Out-of-Order" Curse in Python

Traditional interactive notebooks (like Jupyter with Python) suffer from notorious architectural flaws rooted in mutable global state:

  • Hidden Mutable State: Cells can be executed in arbitrary order. Deleting or modifying an earlier cell leaves mutated objects lingering in the kernel, making results non-reproducible.
  • Re-computation Penalty: Because statements mutate state, changing an upstream parameter often requires a nuclear "Restart Kernel & Run All" operation.
  • Eager Data Ingestion: Ingesting large datasets or infinite sequences immediately forces memory allocations, frequently exhausting RAM or crashing the browser.
  • Heavy Cloud Infrastructure: Running Python requires spinning up remote Docker containers (taking 15–40 seconds on Binder/Colab), incurring recurring hosting bills and data privacy vulnerabilities.

The Pure & Lazy Solution in WebSapl

Modern reactive tools (like Pluto.jl, Observable, and marimo) attempt to build reactive dependency graphs, but constantly fight against variable mutation. In Sapl, mutation does not exist:

Purity + Laziness = Seamless Reactivity:
  • Zero Mutation, Zero Invalidation Conflicts: Functions are pure expressions. A cell's output is an immutable mathematical function of its inputs.
  • Laziness Amortizes Definition Cost: Defining a massive data pipeline, parsing an entire dataset, or generating an infinite stream costs zero machine cycles until a downstream display cell demands it.
  • Automatic Memoization (Thunk Sharing): Once a cell computes a value or Constant Applicative Form (=:), the JMVM updates the thunk in-place (graph reduction). Downstream cells reuse the cached result instantly.

2. Why JMVM is the Ideal Execution Engine for Notebooks

Key virtual machine properties engineered for interactive, exploratory computing.

Pillar 1

Thunk Graph Reduction

Unevaluated expressions live on the heap as lightweight thunk pointers. When an interactive widget or cell requests a slice of data, only the exact needed elements are forced.

Enables natural manipulation of infinite streams (e.g., from 1, prime sieves, event streams) and pagination without pagination logic.
Pillar 2

Persistent Heap & CAFs

When re-evaluating an edited cell, the active VM heap remains alive. Shared global definitions (CAFs declared with =:) retain their evaluated state.

Modifying cell 10 does not cause cell 1 through 9 to be discarded or re-allocated; previous work is instantly accessible.
Pillar 3

Web Worker Isolation

The JMVM engine runs entirely inside an isolated Web Worker (worker.js), communicating with the UI thread via non-blocking messages.

Infinite recursion or heavy graph searches cannot lock the browser tab. The user can cancel, pause, or inspect live execution at 60 fps.

Fault Isolation & Resilient Runtime

In typical compiled languages (C, Rust, Go), a memory violation or stack overflow terminates the operating system process. In the JMVM notebook:

  • Built-in Exception Mechanism: try/catchNr wired into VM execution via SetJMP/GoJMP traps division-by-zero, pattern match exhaustion, and runtime errors cleanly.
  • Symbolic Flight Recorder: If an infinite loop or unexpected branch occurs, the VM flight recorder dumps a human-readable symbolic trace directly into the cell error banner, pinpointing the offending function and argument.

100% Client-Side Privacy & Portability

The entire runtime—compiler, linker, standard library, and virtual machine—is delivered as static WebAssembly and JavaScript assets:

  • Works Offline: Open notebook.html directly from local disk (or host it on GitHub Pages/CDN). No Python kernels, Jupyter servers, or Docker containers required.
  • Zero Server Costs: Universities, schools, and organizations can serve thousands of students simultaneously with zero compute infrastructure costs.
  • Total Data Privacy: User datasets (CSV, JSON, proprietary models) never leave the browser.

3. The Toolchain: In-Memory JIT & Dynamic Code Injection

The subtle technical coordination that enables sub-10ms incremental cell execution.

A naive compiler architecture would write each edited cell to disk, invoke a shell process, compile a full binary, and restart the VM. JMVM replaces this with an entirely in-memory, pure-functional compiler-linker pipeline:

1. Modular Compiler: saplcomp_module

Unlike batch compilers that process whole files, saplcomp_module.cfp is specialized for incremental compilation:

  • Compiles single expressions or isolated top-level functions into binary .jvb byte lists (SM.chunkJvbBytes) in memory.
  • Produces symbol import and export tables describing required external binders.
  • Eliminates full parsing of the standard library by referencing pre-compiled module headers.

2. In-Memory Linker in Pure Sapl (link.cfp)

Dynamic linking is implemented entirely in Sapl itself (laadformaat/link.cfp, LK.lkLink):

  • Calculates relative jump relocations and patches bytecode offsets in memory.
  • Merges the module's constructor and type descriptors with the running program's type dictionary.
  • Returns a self-contained binary payload (LkImg) ready for kernel installation.

3. Hot Installation: lookup "@install:..."

The bridge between Sapl code and the C/Wasm runtime:

  • The VM exposes an internal primitive via lookup "@install:".
  • The runtime appends the newly linked bytecode block directly to the active program[] array without restarting the interpreter loop.
  • applyDynamic immediately executes the newly registered entry point.

4. State Checkpointing (@@values / @@restore)

True session persistence across browser reloads:

  • Serializes evaluated values and global bindings into portable binary representations.
  • Restores full computational graphs when reopening a notebook document, bypassing re-execution of expensive upstream computations.

4. Declarative Graphics & Reactive Elm-Style Interactivity

Turning functional data structures into dynamic visual experiences.

Functional Graphics (grafisch/graphics.cfp)

In pythonic notebooks, generating a plot requires heavyweight libraries (matplotlib, bokeh) serializing millions of coordinates across JSON bridges. In WebSapl, graphics are first-class functional algebraic data types: 

// Algebraic 2D drawing pipeline in Sapl
myPlot = Group [
  Rect 0 0 400 300 (Fill "#1e293b"),
  Polyline (map toCoord (take 100 dataStream)) (Stroke "#38bdf8" 2)
]

The notebook engine renders these structures directly to HTML5 Canvas or SVG with native hardware acceleration, smoothly streaming updates as data arrives.

Elm-Style Interactive Cells (:nbmsg)

Notebook cells can define reactive, self-contained interactive micro-applications using the Elm architecture (Model-View-Update):

  • Model: A pure Sapl data structure representing application state.
  • View: A declarative function transforming the Model into HTML forms, sliders, and buttons.
  • Update: A pure event handler update : Msg -> Model -> Model.
  • Zero Latency: When the user moves a slider, the browser dispatches a message (:nbmsg) to the worker, which evaluates the update function in milliseconds and repaints the view.
