Superseded & Parked Experiments

Not every promising prototype earns a permanent place in the main toolchain. This page documents experiments that were superseded by simpler or faster designs — why they were built, what we learned from them, and where their useful ideas ended up.

1. retag_opt: Whole-Program Stage-4 Retag Optimizer

Core win absorbed into gen1

Built first in Python (retag_opt.py) and then ported to Sapl (sapl_compiler/retagopt.cfp), retag_opt ran between Stage 4 (lazy/strict tagging) and Stage 5 (bytecode emission). Early hand-crafted prototypes looked dramatic: −32% instructions and −49% heap allocations on eval, and −23% / −44% on queens.

What we learned

  • Almost all the gain came from one local pattern: avoiding a thunk for n - 1 or d + 1 when n is already evaluated on that path (affecting 4 of the 13 core benchmarks: eval, queens, hamming, knights).
  • High complexity cost: embedding it in gen1 grew gen1.jvb by 2.1× (~720 KB extra browser download), inline and thunkdoor yielded ≤0.1% and were removed, dead-code elimination broke REPL name lookup, and four subtle semantic bugs had to be fixed.
  • The local rule won: implementing tagLazyMaybe directly in gen1’s stage 2 (stage2_lazytag.cfp, #157) captured 100% of the heap-allocation savings for every program automatically (eval −27.7%, queens −13.0%, hamming −7.6% instructions), with zero whole-program analysis.
  • What remains in --opt: only whole-program “class A” params (omitting eval(x) when every caller passes an evaluated value), worth ~3% wall-clock time on queens and ±0% on eval and hamming.
Sources: Original 8 Nov retag_opt factsheet (historical measurements) and docs/2026-11-09_retag_opt_terugblik_en_kansen.md (retrospective & open local-eagerness ideas).

2. jmvm2c: Bytecode-to-C Continuation Compiler

Superseded by sapl2c

jmvm2c.py translated JMVM bytecode into C by turning every basic block between jump points into a C function chained via [[clang::musttail]].

  • Measured speed: 3,219 ms total on the 12-benchmark suite (more than 2× slower than Clean native’s 1,498 ms) and 442 ms for gen1 self-compilation (vs. 580 ms in runfast).
  • Build weight: gen1 expanded to 9.3 MB of C and took 47 s to compile with clang -O2.
  • Why it hit a ceiling: translating bytecode meant every argument and temporary stayed on the VM stack in memory, clang never saw a whole Sapl function, and returns remained indirect jumps.
  • Replacement: sapl2c translates Stage-4 Retag IR instead — one C function per Sapl function — shrinking gen1 to 2.9 MB of C (4.1 s build), cutting gen1 self-compilation to 248 ms, and running the 13 core benchmarks in 0.34× runfast.

3. jmvm2wat: Direct Bytecode-to-Wasm Compiler

Parked

An experimental AOT translator that lowered JMVM bytecode directly to standalone WebAssembly modules using Wasm return_call tail-call continuations and linear-memory stacks.

  • Measured speed: ~1.5× speedup over the cold Wasm bytecode interpreter in Chrome by eliminating VM dispatch.
  • Why parked: once V8 warms up, the standard 151 KB run.wasm interpreter already runs within 1.38×–1.65× of native C++, without needing per-program Wasm compilation or toolchain complexity.

4. adtmhs: MicroHs Server-Side Route

Parked for interactive use

Compiled Haskell via the MicroHs frontend (adtmhs -Ccache) to Core Sapl (.cfp) and then to JMVM bytecode. Useful as a server-side reference oracle, but superseded for everyday and browser use by Haskell Lite, which is written in Sapl+ and runs directly inside the VM and WebSapl notebooks.
