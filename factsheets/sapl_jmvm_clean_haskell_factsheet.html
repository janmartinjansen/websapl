1. The Big Picture: Architectural Landscape

How functional frontends converge onto shared graph reduction intermediate representations and diverse machine targets.

The system unites pure lazy functional programming languages across four tiers: Frontends (Haskell Lite, MicroHs, Sapl+, Core Sapl, and Clean), Intermediate Representations (Sapl+ AST, Core Sapl, Stage 4 Retag IR, and Clean ABC code), Universal Two-Way Bridges (sapl_naar_abc.py and the newly validated abc2retag.py symbolic decompiler), Virtual & Native Backends (JMVM Native, WebSapl WebAssembly, Clean cg, Clean ABC-Interpreter, and LLVM), and Interactive Environments (WebSapl Browser Notebooks, Desktop Workbench, and REPLs).

The Bidirectional Highway: The system supports seamless translation in both directions:
  • Sapl → Clean ABC: Compile Sapl/Haskell Lite to Clean ABC to leverage Clean's native assembly generator cg (5×–7× faster than bytecode).
  • Clean ABC → Retag → JMVM: Clean programs can be compiled by Clean's compiler to .opt.abc, symbolically decompiled by abc2retag.py to Stage-4 Retag AST, and executed on the JMVM and inside browser WebSapl with zero server overhead!

2. The Frontends: Language Dialects & Capabilities

Different entry points catering to educational notebooks, high-level functional idioms, and systems programming.

Haskell Lite

Frontend • .hs

A lightweight Haskell 2010 dialect implemented entirely in Sapl+ (micro_haskell/hlite/). Runs inside the JMVM both natively and in client-side WebAssembly without requiring any external server.

  • Core Language: Pattern matching (nested, guards, @-patterns, !/~), where, let, case, operator sections, list comprehensions, [1..] ranges.
  • Type System: Full Hindley-Milner type inference with type classes, let-polymorphism, defaulting (Num → Int, fractional → Double), and higher kinds (Functor, Monad).
  • Zero Runtime Dictionaries: Overloaded functions and operators are specialised per type for the whole program. == on an Int becomes a machine comparison; show on Maybe [Int] is a dedicated specialized function.
  • Interactive Notebook Integration: In WebSapl, + Haskell notebook cells share definitions across cells and render live SVG, Canvas, and interactive HTML tables.
data Shape = Circle Double | Rect Double Double deriving Show

area :: Shape -> Double
area (Circle r) = pi * r * r
area (Rect w h) = w * h

Sapl+

High-Level • .spp

An ergonomic superset of Sapl featuring modern language constructs designed for rapid prototyping, rich data manipulation, and clean module boundaries.

  • Named Records: Record construction Rec { a = 1, b = 2 }, dot access r.field, record updates r { field = 3 }, and field pattern matching.
  • Multi-Branch Guards: Pattern equations with boolean guards f x | cond1 = r1 | cond2 = r2.
  • Structural Equality: Deep recursive == and != comparisons on algebraic data structures and strings.
  • Modular Namespaces: Explicit imports with aliases (#import "lib/draw.spp" as D) and name scoping.
  • Lambda Lifting: Inline anonymous functions (\x y -> x + y) automatically lifted into top-level definitions.
record Point = { x :: Int, y :: Int }

distanceSq p1 p2 = 
  let dx = p2.x - p1.x
      dy = p2.y - p1.y
  in dx * dx + dy * dy

Core Sapl

Kernel • .cfp

Simple Applicative Programming Language: the pure, minimal lazy functional core targeting the JMVM stack machine directly.

  • Explicit Laziness & Strictness: Strict arguments explicitly marked with ! (e.g. add !x !y = x + y); lazy arguments defer evaluation into heap-allocated thunks.
  • Explicit Constant Applicative Forms (CAFs): Global shared expressions defined via =: are evaluated once at runtime and memoized permanently.
  • Algebraic Data Types: ::List a = Nil | Cons !a (List a) with direct constructor dispatch.
  • First-Class Exceptions: Robust try expr catchNr handler integrated with VM SetJMP/GoJMP opcodes.
::list = Nil | Cons !x xs

from !a  = Cons a (from (a + 1))
sieve xs = case xs (Cons a as -> Cons a (sieve (filter (nmz a) as)))
primes   =: sieve (from 2)

Clean & ABC

Reference • .icl / .abc

The general-purpose, pure lazy functional language from Radboud University Nijmegen / TOP Software, powering the iTasks task-oriented programming ecosystem.

  • ABC Intermediate Machine: Clean compiles to ABC code—a formal abstract graph rewriting machine featuring a triple-stack architecture (A, B, and C stacks).
  • High-Performance Native Codegen: The Clean cg compiler transforms ABC into native machine code (x86, x86-64, ARM) achieving near-C execution speeds.
  • Dual Interpreter: Clean's abc-interpreter runs native C or WebAssembly in the browser, enabling dynamic functional graph shipping across client-server tiers.
  • Historical Connection: Jan Martin Jansen (2007) and László Domoszlai (2011–2018) originally authored gensapl.icl inside the Clean compiler to emit Sapl code.
module primes
import StdEnv

Start = take 1000 primes
  where
    primes = sieve [2..]
    sieve [p:xs] = [p : sieve [x \\ x <- xs | x rem p <> 0]]

Why abc2retag beats direct stack emulation (abc2jmvm.py):
  • Total Stack Evaporation: ABC basic blocks are saturated with stack shufflers (swap_a, dup_a, updatepop_a, push_b2). abc2retag.py tracks symbolic values through abstract interpretation, eliminating all stack operations at compile time and reconstructing clean functional let-expressions.
  • Huge Instruction Reduction: On sort, instructions dropped by -96.6% (from 9,670M to 333.4M instructions), cutting runtime from 6.49s to 0.27s (24× faster)!
  • Faster than handwritten Sapl on eval: 0.20s vs 0.31s (250M vs 305M instructions); partly because the Clean port carries different strictness annotations than benchmarks/eval.cfp. Clean's interprocedural strictness optimizations carry directly into Retag, reducing GC cycles from 3 to 1!
  • Fixed point: the typed Clean port of gen1 (gen1_naar_clean_getypeerd.py) compiles itself via abc2retag.py on the JMVM byte-for-byte into saplcomp.jmvm (0.55–0.57 s, the same as gen1 itself at 0.56 s).

4. The Universal Bridge: Retag IR & Clean ABC Machine

The two-way operational correspondence between Sapl Stage-4 Retag IR and Clean's ABC abstract graph reduction model.

The Retag Intermediate Representation

In Stage 4 (--emit=retag), the Sapl compiler transforms all implicit lazy reduction dynamics into explicit operational annotations. There is zero ambiguity remaining about evaluation timing.

  • eval(x): Explicit evaluation demand. Forces a thunk into normal form or returns the evaluated value immediately.
  • thunk (f a b): Explicit deferred computation node allocated on the heap with unevaluated arguments.
  • closure (f a): Partial application node capturing unsaturated function parameters.
  • C a b: Fully evaluated algebraic data constructor with boxed or unboxed fields.
  • =:: Constant Applicative Form evaluated at most once and cached globally.

The Clean ABC Machine Model

Clean's ABC machine uses three dedicated stacks to execute lazy functional code with minimal boxing:

  • A-Stack (Argument / Node Stack): Holds references to heap nodes (constructors, thunks, closures).
  • B-Stack (Basic Value Stack): Holds unboxed raw primitive values (integers, booleans, floating-point numbers). Bypasses heap allocation for arithmetic!
  • C-Stack (Control Stack): Stores return subroutine addresses and frame linkages.

Decompilation Mechanics: How abc2retag.py Translates ABC to Retag

1. Symbolic Stack State

Basic blocks are tracked with symbolic expressions in A- and B-stacks. Operations like push_a, swap_a, and pop_a update compiler lists without emitting code. Intermediate stack manipulation evaporates completely.

2. Resolving Graph Mutations

Clean often generates create nodes followed later by fillh or fill_r. The decompiler tracks uninitialized references and resolves them into clean, immutable Retag constructor calls or functional let-bindings.

3. Strictness & Unboxed Primitives

Clean's interprocedural strictness analysis is preserved: primitive values on the B-stack are reconstructed into unboxed arithmetic calls, avoiding redundant boxing and heap allocations.

5. Backends & Execution Platforms

From microarchitectural optimizations on native silicon to zero-overhead client-side WebAssembly.

JMVM Native Engine

Native C++

Ultra-fast stack machine built with Clang [[clang::musttail]] and __attribute__((preserve_none)).

  • 2.5 Billion Op/s: Six VM registers permanently pinned in CPU hardware registers. Eliminates stack frame overhead on dispatch.
  • Superinstruction Fusion: Fuses 7 hot patterns at load time (load_force, jmpt_lv, eval_local), eliminating 21% of all executed instructions.
  • Hardware Case Branching: Pattern matches for constructors 0 & 1 use direct hardware conditional branches (cmp/b.eq), avoiding pipeline stalls.
  • Binary Format (.jvb): Instant startup in ~6 ms without runtime textual parsing.

WebSapl (Browser Wasm)

Client-Side Wasm

Full VM and toolchain compiled to WebAssembly via Emscripten (run.wasm, 151 KB).

  • Zero Server Dependency: Everything (lexer, parser, compiler, VM, graphics) executes in the client browser.
  • Dedicated Stacks in Linear Memory: Does not consume JavaScript call stack; immune to browser recursion limits.
  • High Relative Velocity: Runs at 1.38×–1.65× native speed in Chrome/V8, matching standard C-to-Wasm performance.
  • In-Memory Chunk Loader: Enables live reactive notebooks and interactive REPL sessions.

Clean Native (cg)

AOT Assembly

Compiles ABC intermediate code directly into machine instructions (x86, x86-64, ARM).

  • Peak Performance: 5× to 7× faster than interpreted bytecode; nearly matches hand-written C.
  • Dedicated ABC Stacks: Direct machine register allocation for A, B, and C stack pointers.
  • Self-Hosting Speed: gen1 compiles itself via Clean ABC in just 0.63 seconds native (Sapl → ABC → cg route, earlier measurement). The typed Clean port of gen1 takes 166 ms natively on ARM64 (Clean 3.1), against 557 ms for gen1 on the JMVM and 278 ms for typed Haskell on GHC.
  • Proven Runtime: Decades of mature GC, memory management, and uniqueness typing optimizations.

Clean ABC Interpreter

abci • Native / Wasm

Official Clean bytecode interpreter generated from a formal specification (interpretergen-c and interpretergen-wasm).

  • Dynamic Interworking: Enables shipping lazy thunks and functions between servers and clients.
  • Sandboxing: Safe isolated evaluation of untrusted functional bytecode.
  • Performance: Comparable to JMVM native; slightly slower in WebAssembly unless locals optimization is applied.

AOT C Translation (jmvm2c)

Experimental AOT

Ahead-of-time compiler converting JMVM bytecode into continuous C functions connected by musttail.

  • 1.7×–2.4× Speedup: Delivers significant acceleration over the bytecode interpreter.
  • Clang Optimization: Clang extracts additional hardware pipeline throughput from structured C continuations.
  • Tradeoff: Large generated C files (gen1 is ~8.3 MB C) with compilation taking ~41s under -O2.

Direct Wasm (jmvm2wat)

Experimental AOT

Directly translates bytecode to standalone WebAssembly modules using return_call continuations.

  • 1.5× Speedup in Chrome: Runs faster than the cold Wasm interpreter.
  • Eliminates VM Dispatch: Bytecode instructions turn directly into Wasm instructions with linear memory stacks.

Key Ecosystem Synthesis

The convergence of Haskell Lite, Sapl(+), JMVM, and Clean ABC creates a completely closed, bidirectional functional computing stack: developers gain the ergonomic clarity and educational appeal of standard Haskell in frictionless, zero-server browser notebooks (via WebSapl), the modular simplicity of a lightweight stack machine (JMVM), an immediate route to near-C native execution speed by targeting Clean's cg compiler via Retag → ABC, and the ability to decompile Clean ABC programs into Retag AST via abc2retag.py, enabling Clean programs to run directly on the JMVM and inside browser notebooks!
