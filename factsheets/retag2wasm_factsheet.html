How retag2wasm Translates Retag Straight to WebAssembly

retag2wasm takes the same Stage-4 Retag IR as sapl2c but writes binary .wasm itself, with no C, no Clang and no Binaryen, in about a thousand lines of Sapl that run inside the JMVM’s own wasm build. This sheet explains the translation, the trade-offs that were measured along the way, and how it relates to sapl2c, with real Retag, C and WAT side by side.

1. At a Glance

QuestionAnswer (measured, dated)
What goes in, what comes out? Stage-4 Retag text (x.retag.txt, from gen1 --emit=retag, or from abc2retag for Clean) → x.wasm + x.json (table and data sizes for the loader).
Who writes the wasm? sapl_compiler/sapl2wasm.cfp (Sapl, ~1000 lines), imported by sapl2c.cfp; reference in Python: experiments/sapl2c/wasm/r2w/sapl_naar_wasm.py. Byte-identical output for all 13 benchmarks and gen1 (20 Nov 2026).
How fast? 1.13× the time of emcc -O2 on the same IR (Node 26/V8, warm, geometric mean over 14 programs, 20 Nov 2026 evening), about 88% of clang’s speed. In the browsers ~0.30× the time of jmvm.wasm, for the programs that fit the ~1 MB stack (20 Nov 2026).
Where does it run? The whole chain runs in wasm: gen1 → Retag → sapl2wasm (both in jmvm.wasm) → WebAssembly.compile → run against a 60 KB runtime. Demo: sapl2wasm.html.
What does it not do? try/catch and float literals (the generator stops with a message). The browser call stack is the main limit; see section 6.

Browser tables, stack measurements and the Safari trampoline numbers live in the WebAssembly backends factsheet; this sheet explains why the code looks the way it does.

2. The Pipeline: Only the Last Step Is New

Sapl / Haskell-lite source ──► gen1 ──► Stage-4 Retag (x.retag.txt) ◄── abc2retag ◄── Clean .opt.abc
                                              │
                          sapl_naar_c.py / sapl2c.cfp:  the shared front
                          IR: assignments, if/case in tail position, liveness,
                          which variables to spill, merged heap checks,
                          non-pointer proofs, C expressions kept as text
                          ┌───────────────┴────────────────┐
                          ▼                                ▼
                emit C text (sapl2c)             parse the C expressions,
                  ──► clang -O2                  emit wasm bytes (sapl2wasm)
                  ──► native binary / emcc          ──► x.wasm + x.json
                                                          │
                       rt.h ──► rt_wasm.c ──► emcc (once) ──► rt.js + rt.wasm (60 KB)
                                                          │
                       r2w_laad.js: start runtime, reserve table and data, instantiate, call main

sapl_naar_wasm.py imports everything of sapl_naar_c.py up to the IR; only the writer is new. sapl2c.cfp imports sapl2wasm.cfp and looks at the suffix of the target file: .c gives C, .wasm the direct form with tail calls, .k.wasm the own-stack (continuation) form and .t.wasm the trampoline form for Safari.

The pragmatic choice: the IR still carries C expressions as text

The shared IR holds expressions such as SL(3), CON(0), PTR(p_xs)[1] or the fast and slow arithmetic paths as C strings. sapl2wasm therefore contains a small parser for exactly that C subset and translates the parsed expression to wasm instructions. That is why the first attempt (20 November) already had all 14 programs correct on its first full run: the hard decisions came from the IR, only the writing was new. It is also why the generator is ~2.7× slower than gen1 itself (1,012 ms against 376 ms for gen1 translating itself, 20 Nov 2026): every expression is re-parsed from text and the bytes are built with many appends. For ordinary programs the translation takes a few to a few tens of milliseconds, so this has not been worth fixing yet.

3. The Translation Scheme

AspectIn wasmWhy
Values Tagged i64 cells, as on the VM and in sapl2c: low bits 00 = int (SL(n) = n<<2), 01 = heap pointer (ptr|1, not shifted), 11 = char. The same memory model means the same GC and the same runtime for every back-end. In wasm32 a pointer is the low 32 bits of the cell: (i32.and (i32.wrap_i64 v) (i32.const -4)) is PTR(v).
Function signature (i32 hp, i32 sp, i64 a0..a5) → (i64 value, i32 hp) The heap pointer travels in a wasm local, not in memory. The multivalue return replaces the R struct of the C version.
Tail calls and loops return_call for a tail call to another function, (loop $top) + br $top for goto top. Same uniform convention as MUSTTAIL in C; self-recursion becomes a real loop.
Variables Retag variables become wasm locals. The single biggest reason for the speed (section 5).
Moving GC Live heap pointers are spilled to the shadow stack in linear memory (sp, 8 bytes per cell) around every GC-capable point and reloaded afterwards; variables proven to be non-pointers are never spilled. Locals are invisible to the collector. Spill decisions come unchanged from the shared IR.
Allocation One merged heap check per straight-line block, then bump allocation: hp + n*8 > *hendp → rt_gc. Fewer checks, smaller code. hendp lives in memory so the runtime can move it.
Laziness EVALK inline: pointer? thunk? then spill, call_indirect the thunk entry through its FnDesc, reload; evaluated thunks are read directly. Most evaluations hit an already-evaluated value; the common case should cost a few instructions.
Static data FnDescs, strings and names sit at dbase (a block from the runtime’s malloc), functions go in the shared table from tbase; x.json says how much of each. One program module is instantiated against a once-built runtime module.

4. Examples: Retag → C → WAT

The Retag and C below are produced by ./compile --emit=retag and sapl_naar_c.py; the WAT by sapl_naar_wasm.py. The Sapl generator writes the same bytes directly, without WAT: for the examples here the .wasm from sapl2c.jmvm is byte-identical to wat2wasm of the Python output. WAT is shortened and re-indented by hand (... marks cuts); the generator writes it all on long lines. Both programs were run (r2w_node.js): fib 38 gives res: 126491971, the list program res: 55 (4.9 KB and 3.3 KB of wasm, helpers included).

Example A: nfib: no heap, no spills, two results

nfib !n = if (n < 2) 1 ((nfib (n - 1) + nfib (n - 2)) + 1)

The C version (sapl2c):

static R f_nfib(cell* hp, cell* sp, cell p_n, cell u1_, ..., cell u5_) {
  cell v1_r, v2_nfib, v3_r, v4_nfib, v5_r, v6_r;
 top: ;
  if ((LIKELY(!((p_n) & 3)) ? (p_n < SL(2)) : cmp_slow('<', p_n, SL(2)))) {
    RET(SL(1));
  } else {
    v1_r = (LIKELY(!((p_n) & 3)) ? (p_n - SL(1)) : arith_slow('-', p_n, SL(1)));
    CALL(v2_nfib, f_nfib(hp, sp + 0, v1_r, 0, 0, 0, 0, 0));
    v3_r = (LIKELY(!((p_n) & 3)) ? (p_n - SL(2)) : arith_slow('-', p_n, SL(2)));
    CALL(v4_nfib, f_nfib(hp, sp + 0, v3_r, 0, 0, 0, 0, 0));
    v5_r = (LIKELY(!((v2_nfib | v4_nfib) & 3)) ? (v2_nfib + v4_nfib) : arith_slow('+', ...));
    v6_r = (LIKELY(!((v5_r) & 3)) ? (v5_r + SL(1)) : arith_slow('+', v5_r, SL(1)));
    RET(v6_r);
  }
}

The WAT version:

(func $f_nfib (type $K)
      (param $hp i32) (param $sp i32) (param $p_n i64) (param $u1_ i64) ... (param $u5_ i64)
      (result i64 i32)
  (local $v1_r i64) (local $v2_nfib i64) (local $v3_r i64) (local $v4_nfib i64)
  (local $v5_r i64) (local $v6_r i64)
  (loop $top
    (if (if (result i32)
            (i32.eqz (i64.ne (i64.and (local.get $p_n) (i64.const 3)) (i64.const 0)))   ;; tag test
            (then (i64.lt_s (local.get $p_n) (i64.shl (i64.const 2) (i64.const 2))))    ;; n < SL(2)
            (else (call $cmp (i32.const 60) (local.get $p_n) (i64.shl (i64.const 2) (i64.const 2)))))
      (then (return (i64.shl (i64.const 1) (i64.const 2)) (local.get $hp)))             ;; RET(SL(1))
      (else
        (local.set $v1_r
          (if (result i64) (i32.eqz (i64.ne (i64.and (local.get $p_n) (i64.const 3)) (i64.const 0)))
            (then (i64.sub (local.get $p_n) (i64.shl (i64.const 1) (i64.const 2))))
            (else (call $rt_arith (i32.const 45) (local.get $p_n) (i64.shl (i64.const 1) (i64.const 2))))))
        (call $f_nfib (local.get $hp) (local.get $sp) (local.get $v1_r)
              (i64.const 0) (i64.const 0) (i64.const 0) (i64.const 0) (i64.const 0))
        (local.set $hp) (local.set $v2_nfib)      ;; two results: pop hp, then the value
        ... same for nfib (n - 2) -> $v4_nfib ...
        (local.set $v5_r ...)  (local.set $v6_r ...)   ;; the two additions, fast path + $rt_arith
        (return (local.get $v6_r) (local.get $hp)))))
  (unreachable))
  • n is declared strict (!n, found by the strictness inference), and the analysis proves that n and the call results are non-pointers, so there are no spills and both recursive calls pass the same $sp (sp + 0 in C).
  • The C ternary LIKELY(!(x & 3)) ? fast : slow becomes an if (result i64). The slow path calls $rt_arith with the operator as an ASCII code (45 = -, 43 = +, 60 = <).
  • (i64.shl (i64.const 2) (i64.const 2)) is SL(2) left unfolded: the generator does not fold constants and leaves that to the engine. Whether folding in the generator would gain anything has not been measured.
  • After a non-tail call, (local.set $hp) (local.set $v2_nfib) pops the two results (the value is below, the heap pointer on top).

Example B: upto: allocation, a thunk and a Cons in one block

upto !a !b = if (a > b) Nil (Cons a (thunk (upto (a + 1) b)))
if ((LIKELY(!((p_a | p_b) & 3)) ? (p_a > p_b) : cmp_slow('>', p_a, p_b))) {
  v1_Nil = CON(0);
  RET(v1_Nil);
} else {
  v2_r = (LIKELY(!((p_a) & 3)) ? (p_a + SL(1)) : arith_slow('+', p_a, SL(1)));
  if (HEAPFULL(7)) {  GC(0);  }
  { cell* r_ = hp; hp += 7; CNT_CREATE(2);
    v3_thunk = TAGP(r_ + 0);
    v4_Cons  = TAGP(r_ + 4);
    r_[0] = ADM_THUNK(2); r_[1] = v2_r; r_[2] = p_b; r_[3] = FNCELL(d_upto);
    r_[4] = ADM(T_CONSTR, 5, 1, 3); r_[5] = p_a; r_[6] = v3_thunk;
  }
  RET(v4_Cons);
}
(else
  (local.set $v2_r ...)                                  ;; a + 1, fast path + $rt_arith
  (if (i32.gt_u (i32.add (local.get $hp) (i32.const 56))   ;; HEAPFULL(7): 7 cells x 8 bytes
                (i32.load (global.get $hendp)))
    (then (local.set $hp (call $rt_gc (local.get $sp) (local.get $hp)))))
  (local.set $r_ (local.get $hp))
  (local.set $hp (i32.add (local.get $hp) (i32.const 56)))
  (local.set $v3_thunk (i64.extend_i32_u (i32.or (i32.add (local.get $r_) (i32.const 0))  (i32.const 1))))  ;; TAGP
  (local.set $v4_Cons  (i64.extend_i32_u (i32.or (i32.add (local.get $r_) (i32.const 32)) (i32.const 1))))
  (i64.store offset=0  (local.get $r_) (i64.const 274877906947))          ;; ADM_THUNK(2)
  (i64.store offset=8  (local.get $r_) (local.get $v2_r))
  (i64.store offset=16 (local.get $r_) (local.get $p_b))
  (i64.store offset=24 (local.get $r_) (i64.extend_i32_u (i32.add (global.get $dbase) (i32.const 0))))  ;; FNCELL(d_upto)
  (i64.store offset=32 (local.get $r_) (i64.const 206426886155))          ;; ADM(T_CONSTR,5,1,3)
  (i64.store offset=40 (local.get $r_) (local.get $p_a))
  (i64.store offset=48 (local.get $r_) (local.get $v3_thunk))
  (return (local.get $v4_Cons) (local.get $hp)))
  • HEAPFULL(7) is hp + 56 > *hendp: seven cells (a 4-cell thunk plus a 3-cell Cons) of 8 bytes. One check covers both objects.
  • The admin words are constants. 274877906947 = (4<<36) | 3 is a 4-cell thunk node; 206426886155 is ADM(T_CONSTR, 5, 1, 3) (type 11, type id 5, constructor 1, size 3).
  • C’s TAGP(r_ + 4) is (r_ + 32) | 1. The thunk’s last cell points at its FnDesc inside the data block ($dbase + 0).
  • Only the GC path touches the runtime; the allocation itself is seven stores.

sumList !xs acc = case xs (Nil -> acc) (Cons x rest ->
                    sumList (eval(rest)) (thunk (sumList_1 acc x)))

  • The self tail call sumList rest thunk reassigns the parameters and branches to the top of the loop: constant stack, no return_call.

Example D: the same nfib in the own-stack (continuation) form

Selected with R2W_CPS=1 in the Python generator or a .k.wasm target in the Sapl generator:

(func $f_nfib ...                                   ;; after the first recursive call has to come back:
  ...
  (if (i32.gt_u (local.get $sp) (global.get $kspl)) (then (call $kover) (unreachable)))   ;; own-stack bound
  (i64.store offset=0 (local.get $sp) (local.get $p_n))                      ;; live value  -> own stack
  (i64.store offset=8 (local.get $sp) (<table index of $f_nfib_k1m> << 2))   ;; continuation -> own stack, as a tagged int
  (return_call $f_nfib (local.get $hp) (i32.add (local.get $sp) (i32.const 16)) (local.get $v1_r) ...))

;; "RET(x)" is no longer a return: pop the continuation index from the stack and jump to it
(return_call_indirect (type $K) (local.get $hp) (i32.sub (local.get $sp) (i32.const 8)) <x> ...
    (i32.wrap_i64 (i64.shr_u (i64.load (i32.sub (local.get $sp) (i32.const 8))) (i64.const 2))))

(func $f_nfib_k1r ...      ;; continuation: runs after nfib (n-1) returned in $kv, with p_n reloaded from $k1
  (local.set $v2_nfib (local.get $kv))
  (local.set $p_n (local.get $k1))
  (local.set $v3_r ...)    ;; n - 2
  ... push v2_nfib and the index of $f_nfib_k2m, return_call $f_nfib again ...)
(func $f_nfib_k2r ...)     ;; the second continuation: add, add 1, RET
  • A call that is not a tail call becomes: store the live values, store the table index of the continuation, return_call the callee. RET pops that index and jumps to it. The engine’s call stack never grows.
  • Each call site gets its own small function (_k1r, _k2r) with the rest of the statements. That is easy because if and case only occur in tail position in the IR: after a call comes always “the rest of the same list”. A continuation with at most 5 live values exists in two forms: _k1r receives the values in registers, _k1m first loads them from the own stack and jumps there; after an eval of an already-evaluated value the code jumps to the register form directly.
  • The cost: a bound check per frame ($kspl) and an indirect jump per return.

5. Design Decisions and What They Were Worth

DecisionAlternativeWhat was measured
Start from Retag, not from bytecode Translate JMVM bytecode to wasm (tried twice) Bytecode still behaves like a stack machine. Jul–Sep 2026 the first attempt was slower than the interpreter; 29 Sep (jmvm2wat, explicit stack) ~1.5× faster, too little. From Retag 3–4× (20 Nov). A compiler over a fast interpreter pays off only around ~3×.
Write locals ourselves Rely on clang or wasm-opt Experiment B (20 Nov): emcc -O1 is 0.95× the time of -O2, -O2 -fno-inline 1.01×, but -O0 4.49×, and wasm-opt -O3 over -O0 output 4.43×. Clang’s big win is variables in locals (mem2reg), not inlining. Retag already has whole functions with named variables, so we can do that part directly.
No Binaryen Run wasm-opt over the output ~5% extra at most on the generated modules (20 Nov). The generator is small enough to run inside the browser; adding a post-pass tool for ~5% was not worth it.
Runtime as a separate module One module with everything rt.h is built once with emcc (60 KB) and shared by all programs: GC, floats, I/O, strings, files. The per-program parts of rt.h are hooks (sapl_start, con_name_of, lookup_find) or fixed bounds (NCAFS/NCON at 4096). Cost: every runtime call crosses a module boundary and cannot be inlined.
Hot paths in the program, cold paths in the runtime Everything via the runtime first Moved in, in order (20 Nov): fast path of ap1 (1.28× → 1.26× emcc); truth() inline (knights 1.46 → 1.17); ap1_slow and apply_n (twice 1.42 → 0.95, mean 1.20 → 1.15); the five string/compare helpers (eval2 1.45 → 1.25, gen1 1.18 → 1.06, mean 1.17 → 1.13). Counting runtime calls (R2W_TEL=1) showed 43 million rt_strlen calls in eval2 before that last step.
Constants vs imported globals Bake data, heap-end and constructor-table addresses in as constants No difference on 5 programs (20 Nov); the module stays independent of where the loader puts the data.
Multivalue return Return the value, write hp to memory On the sapl2c + emcc route (Node, 20 Nov): fib 262 → 133 ms, gen1 313 → 266 ms; mean 1.62× → 1.35× native.
Reuse the IR, parse C text Rewrite the IR as wasm-ready trees Fast to build and verifiable (byte-identical outputs), at the price of a slow generator (~2.7× gen1).
An unexplained cost: after the string helpers went into the program, fib became ~5% slower (in Chrome ~10%) though it uses no strings. Routing $cmp through the runtime again did not bring it back, so the inlining guess was wrong; it looks like a layout or tiering effect in V8. hamming showed a similar unexplained gain. Small wasm differences of this size should not be explained without a measurement.

6. The Stack: One Problem, Three Remedies

The direct form uses the engine’s call stack for every non-tail call (an EVALK, a strict argument, an over-saturated call). Browsers give a wasm module roughly 1 MB and web pages cannot enlarge it; gen1 needs ~0.7–1.3 million calls of depth. Natively sapl2c has a 4 GB thread stack. The remedies, each of which was built and measured:

FormHowPriceWorks
Direct (.wasm)engine stacknone: 1.13× emcc -O2 (Node, 20 Nov) 9 of 14 in Chrome/Firefox, 11 of 14 in Safari (20 Nov); 14 of 14 in Node with a 2 GB stack
JSPI segments (R2W_SEG)a depth counter on every non-tail call; at the limit, continue on a fresh JSPI stack +23% even for programs that never switch (counter on every call); Firefox ~0.3 ms per switch (gen1: 4.7 s) (20 Nov) 14 of 14 in Node, Chrome, Firefox; not in Safari
Own stack (.k.wasm, R2W_CPS)continuation form, see example D ~1.12× emcc -O2 in Node (equal to direct, deep programs even faster); 20 Nov: Chrome 0.34× jmvm.wasm, Firefox 0.59×, Safari 1.38× (slower than the interpreter) 14 of 14 everywhere
Own stack, trampoline (.t.wasm)each function returns the next state, sapl_start loops (chunks of 1000 jumps) Made for Safari, where every return_call costs ~7× an ordinary call (JavaScriptCore): 0.48× jmvm.wasm there (25 Nov), but 3–7× slower than tail calls in Chrome and 1.8–3.3× in Firefox 13 of 13 benchmarks in all three (25 Nov)

The demo page sapl2wasm.html shows JMVM, direct and own stack side by side and picks the own-stack form per browser: tail calls in Chrome and Firefox, the trampoline in Safari and on iOS. The details and the tables are in the backends factsheet.

In short: sapl2c buys speed from a mature optimiser and needs a C toolchain; retag2wasm keeps ~88% of that speed with a tool that fits in the browser, and it inherits every correctness decision (spills, GC safety, strictness) from the shared IR.

8. Limitations and How to Use It

  • try/catch is not supported (setjmp has no direct wasm equivalent). Nothing in the benchmarks or gen1 uses it.
  • Float literals are not supported: the f32 bits must be derived from the decimal text, which Sapl cannot do without a primitive.
  • No numeric literal above 32 bits in the source of the generator, so WebSapl can load it (jmvm.wasm rejects 8-byte words); admin words are computed.
  • Memory is a fixed heap per module (wasm32: at most 4 GB); the runtime has 8M or 16M cells (RT8/RT16).
  • The stack: see section 6.

Translate and run a program (from the repo root; sapl_compiler/sapl2c.jmvm is built with ./compile sapl_compiler/sapl2c.cfp and is not in git):

./compile prog.cfp --emit=retag                 # -> prog.retag.txt
bash experiments/sapl2c/wasm/r2w/bouw.sh UIT    # once: runtime -> UIT/rt.js + rt.wasm
printf 'prog.retag.txt\nUIT/prog.wasm\nUIT/prog.json\n' | ./runfast sapl_compiler/sapl2c.jmvm
node experiments/sapl2c/wasm/r2w/r2w_node.js UIT UIT/prog.wasm

The suffix chooses the form: prog.k.wasm for the own stack, prog.t.wasm for the trampoline. The Python reference:

python3 experiments/sapl2c/wasm/r2w/sapl_naar_wasm.py prog.retag.txt prog.wat prog.json   # R2W_CPS=1 for the own stack
wat2wasm --enable-tail-call prog.wat -o prog.wasm
bash experiments/sapl2c/wasm/r2w/toets.sh UIT            # all 14 against ./runfast
bash experiments/sapl2c/wasm/r2w/toets_sapl.sh UIT       # Sapl generator = Python generator, byte for byte
