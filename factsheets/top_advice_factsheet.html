Advice for TOP Software: Lead with the Toolchain, Treat Native as an Add-on

What the JMVM / Sapl experiments suggest for Clean, based on measurements of 13 November 2026 (Apple M4, one machine). The strongest argument is not speed.

1. Recommendation

Lead with the interpreter and toolchain

One small VM, with compiler, linker, typechecker and REPL as bytecode running on it, on both sides of the wire. That is what answers “Clean in the browser”, and no native backend competes with it.

Treat native code as an add-on

For servers or hot code where speed matters. It needs nothing changed in the VM, and on small programs it reaches Clean native. On large typed code Clean’s cg stays ahead.

2. If TOP goes native: the lesson about the input

The level of the intermediate language mattered more than the backend. The same clang -O2 gave a C program that was 2.2× slower than Clean native when fed from stack-machine bytecode (jmvm2c), and one that matches or beats it on small benchmarks when fed from a structured form with named variables, explicit case trees and explicit thunks (Retag, via sapl2c). ABC is stack code, like the JMVM bytecode. Whoever starts from ABC should expect to rebuild that structure first, as abc2retag does.

  • Keep the types. Retag is untyped, which is where the gap on large typed code comes from. A type side file (annotations only, erasable) is the natural next step; it is untested. Upper bound for the simplest form (tag checks removed on integer code): −5.5% on ten safe benchmarks, up to −17% on fib.
  • Do not expect to beat cg on large typed programs. Clean native took 164–173 ms on the typed self-compile, the Retag route 234 ms.

The benchmark average is not an average program. The two benchmarks that resemble a compiler (parsetest, eval) are where the Retag route is slowest (1.4–1.75×), and the self-compile lands in the same range.

4. What has not been measured

  • An iTasks-sized application: speed, and compile time (the typed self-compile is 3.7 MB of C and takes 4.2 s in clang -O2).
  • Parts of Clean the benchmarks do not use: uniqueness and arrays, records, ccall, dynamics.
  • The native route in WebAssembly, and compatibility of the heap and descriptor layout with the ABC interpreter (iTasks ships graphs between native server and browser).
  • Windows (musttail needs clang). One machine; Clean native ran in a Linux VM, with noise of 15–20% on some benchmarks.
Suggested next step with TOP: measure one real iTasks application through the existing abc2retag route: speed, compile time and graph compatibility. A day of joint work would turn this advice from a plausible argument into a measured one.
