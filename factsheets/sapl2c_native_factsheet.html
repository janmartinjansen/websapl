Sapl to native code via C: one C function per Sapl function

sapl2c translates gen1’s Stage-4 retag form into C, one C function per Sapl function, on the JMVM’s own memory model and GC — optionally the VM’s own runtime code. All 13 core benchmarks run in 0.33× the interpreter’s time, faster than Clean’s native code generator and on par with GHC, and the Sapl compiler compiles itself natively in 244 ms.

Pipeline

x.cfp→ gen1 --emit=retag→ sapl_naar_c.py→ x.c + rt.h→ clang -O2→ native binary

The retag form already has explicit eval, thunk and closure, strictness annotations and lifted helper functions, so each line becomes one C function. With -DVM_RT, heap, copying GC, strings, packed arrays and the CAF table are the VM’s own code (vm/vm.cpp, unchanged, through vm_brug.cpp); both runtimes give identical results at the same speed.

The untyped ports do the same work as Sapl (one Val type, every number a node); there sapl2c is the fastest. With types, Clean’s front end keeps numbers unboxed and is 1.5× faster.

Build time. gen1 becomes 2.9 MB of C: retag 0.42 s, generator 0.22 s, clang -O0/-O1/-O2 1.1/3.4/4.1 s. The resulting compiler self-compiles in 739/271/282 ms, so -O1 is the sensible default. The benchmarks build in 0.06–0.6 s. (jmvm2c: 9.3 MB, 47 s.)

Why the earlier jmvm2c was slow

jmvm2c translated the bytecode: every piece between two jump points became a C function chained with musttail, the interpreter without dispatch. Every argument and temporary stays on the VM stack in memory, clang never sees a whole Sapl function, and returns are indirect jumps.

Design

callsEvery function is R f(cell* hp, cell* sp, cell a0 … a5); R = {value, hp} comes back in two registers. One uniform signature, so every tail call is musttail; further arguments go on the shadow stack.
GC rootsThe shadow stack is the VM stack. A value that may be a pointer and is still needed after a call goes to sp[0..k-1] before the call and is read back after. Cells are tagged, so no stack maps are needed.
proofsA variable is not saved when it is proven not to be a pointer on the current path. Three kinds — int, non-pointer (int, char or float), any — and a fixpoint over all functions for the kind of each result.
lazinessThunks are VM CLOSURE nodes; evaluation is an inline tag test, and the thunk entry evaluates and overwrites the node. One C frame per level of a thunk chain: beyond ~50 nested calls the return predictor fails (4.8 ns instead of 0.7 ns per return).
languageFloats, strings, I/O, CAFs, try/throw/error (_setjmp with the VM’s handler semantics), reflection, mutable arrays, catchable VM faults with the VM’s messages.

Correctness

  • The 13 benchmarks: byte-identical output and equal allocation counts, with both runtimes.
  • GC stress: a GC at every heap check on small inputs, every 1009th on full inputs, the old half-space poisoned after each GC. A deliberately dropped root fails at once.
  • gen1: the fixed point (also under GC stress), and the same output as the VM’s gen1 for all benchmarks in the jmvm, jvb and retag stages; all 1,368 tail calls are jumps.
  • A sweep over 149 programs in tests/ and examples/: 105 identical, 6 refused (pack/unpack), 8 known differences.

The growing heap

The heap starts at 8 MB and grows fourfold after a GC when more than a tenth is live (both half-spaces reserved at full size; untouched pages cost nothing). A 192 MB allocation area does not fit in the cache. Against the fixed heap: sprimes −45%, match and prolog −21%, hamming −18%, queens −16%, primes −12%, eval −10%, parsetest +3%, gen1 252 → 248 ms. Growing at 1/3 instead of 1/10 made gen1 7% slower (18 GCs instead of 7).

Not supported

pack/unpack (they serialize bytecode), lookup "@...", and a stack overflow as a catchable error (the C stack has no guard page yet). Not for the browser: the C stack is the call stack. Source: docs/2026-11-11_sapl2c_native_factsheet.md, experiments/sapl2c/.
