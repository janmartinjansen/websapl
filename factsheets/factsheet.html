1. JMVM: Architectural Foundations & Recent Performance Revolution

From lazy graph reduction to high-throughput direct machine dispatch on modern silicon.

Architectural Foundations

JMVM is a stack-based virtual machine purpose-built for executing lazy, pure functional programming languages (sharing heritage with the Clean ABC machine and GHC's Spineless Tagless G-machine).

  • Dual Stack Design: Dedicated evaluation stack (sp) for intermediate values and arguments, paired with an independent control stack (csp) for function returns and thunk updates.
  • Graph Reduction & Thunk Sharing: Unevaluated expressions are allocated on the heap (hv) as thunks. When forced, the thunk is overwritten in-place with its evaluated result, preventing duplicate computations.
  • Explicit Evaluation Semantics: Crisp separation between unevaluated closures (eval / force) and unboxed/evaluated constructor values and primitives.
  • Constant Applicative Forms (CAFs): Global constants and shared closures are evaluated at most once and cached in a global CAF table.

Recent Evolution (July – November 2026)

Over recent months, JMVM transitioned from a monolithic interpreter to a highly modular, hardware-optimized runtime platform:

  • Binary Format (.jvb): Introduction of a compact binary loading format. The native VM and WebAssembly client completely eliminated runtime textual bytecode parsing, reducing module/REPL startup from ~117 ms to ~6 ms.
  • Modular C Architecture: Instruction bodies partitioned into clean, self-contained units (vm/instr/*.c), driven by a specification table (vm/instructies.tab) and an automated Sapl code generator (vm/genereer.cfp).
  • Ring-Buffer Flight Recorder: The debug build (runswitch-debug) maintains an in-memory ring-buffer of the last 4,096 instructions, automatically dumping symbolic backtraces upon crashes or hangs (SIGALRM).

The Three Waves of Performance Optimization (Fall 2026)

Phase 1 • Oct 24, 2026

Musttail Direct Threading

Replaced monolithic computed goto with tail-call direct threading using [[clang::musttail]] and __attribute__((preserve_none)).

Impact: Eliminated Clang register allocation bottlenecks. Each opcode became an independent function with 6 pinned CPU registers. fib runtime was cut in half (−54.3%, 2.19× faster).
Phase 2 • Nov 1, 2026

Superinstructions (Fusion)

During bytecode load time (makeCode), the loader fuses 7 hot instruction sequences: jmpt_lv, load_force, eval_local, load2, etc.

Impact: Eliminated 21% of all executed VM instructions and stack round-trips. Major speedups on memory-bound workloads: sprimes dropped from 1411 ms to 806 ms (−43%).
Phase 3 • Nov 2, 2026

Hardware Case Branching

Hardware profiling with Apple kperf revealed severe pipeline stalls caused by a 4-deep dependent memory read chain in jmpt. Replaced with direct hardware conditional branches (cmp/b.eq) for constructors 0/1.

Impact: Hardware branch predictors now predict pattern matching targets without pipeline bubbles. knights improved by −38%, and self-compilation of gen1 sped up by −25%.

2. Sapl: The Language & The Retag Compilation Pipeline

An expressive pure functional language and its 7-stage formal transformation.

The Sapl Language & Extensions

Sapl (Simple Applicative Programming Language) combines theoretical clarity with practical expressiveness, making lazy graph reduction explicit and deterministic.

  • Sapl+ (.spp) Preprocessor: Enriches the language with modern features: typed records with dot access, nested deep pattern matching, multi-branch guards, modular qualified imports (import M as Mod), and lambdas with automatic lambda lifting.
  • Automatic Strictness Inference: Built-in abstract interpretation (strictness.cfp) automatically deduces strict argument positions and annotates them with !, eliminating redundant thunks without manual developer intervention.
  • Explicit CAFs (=:): Formal CAF semantics guarantee that shared constant closures and partial applications are safely evaluated once and preserved across calls.
  • Dynamic Typing & Reflection: Built-in primitives for lookup, typeId, and applyDynamic, enabling dynamic dispatch and plug-in architectures.
  • Robust Exception System: First-class try/catchNr mechanism wired directly into VM dispatch via SetJMP/GoJMP.

The Pivotal Retag Intermediate Format

The cornerstone of the compilation pipeline is the retag intermediate representation (grounded in the formal IFL 2016 model). It translates implicit laziness into unambiguous evaluation and allocation operations.

Why Retag is essential:
  • Semantic Transparency: Every evaluation point (eval), thunk creation (thunk), and partial application (closure) is made explicit before code generation.
  • Universal Intermediate Representation: Acts as an abstract bridge, decoupling frontends from machine backends. Alternative codegen targets (such as the experimental Clean ABC backend) attach directly to retag.
  • Modular Tooling: retagcomp and retaglink enable independent per-module compilation and cross-module optimizations.

The --emit=retag flag allows developers to inspect the exact annotated intermediate representation at any point.

Sapl Source Code (primes.cfp)

// Infinite stream generation and lazy sieve filtering
::list = Nil | Cons !x xs

from !a  = Cons a (from (a + 1))
sieve xs = case xs (Cons a as -> Cons a (sieve (filter (nmz a) as)))
primes   = sieve (from 2)

Contrast between strict and lazy arguments: from !a has a strict parameter, while sieve xs receives its stream lazily.

Emitted Retag Form (primes.retag.txt)

// Stage 4: Strict argument vs lazy argument forcing
from !a  = Cons a (thunk (from (a + 1)))

sieve xs = case (eval(xs)) (Cons a as -> 
             Cons a (thunk (sieve (thunk (filter (closure (nmz a)) as)))))

Retag contrast: In from !a, strict a needs no eval. In sieve xs, lazy xs is explicitly demanded via eval(xs). Filter predicate is a closure, and stream tails are deferred as thunk.

3. Tooling: Self-Hosting & On-the-Fly In-Memory JIT

A self-hosted compiler, in-memory linking, and instantaneous dynamic code injection.

The Self-Hosting Compiler ("gen1")

As of September 2026, the primary production compiler is 100% self-hosted: written in Sapl and running on JMVM (saplcomp.jmvm).

  • Fixed-Point Stability: The compiler compiles its own source code to produce byte-for-byte identical bytecode, verified by ./check_bootstrap in ~12 seconds.
  • Haskell Anchor: To eliminate circular bootstrapping risks, a toolchain generator maintains a typed Haskell equivalent (saplcomp_typed.hs) which, when built with GHC, emits the exact same bytecode.
  • Compiler Velocity: Thanks to recent VM execution optimizations, gen1 self-compiles its entire codebase in just 598 ms on an Apple M4 (typed Haskell on GHC -O2: 295 ms).
  • Native Compiler: Compiled to C with sapl2c, gen1 self-compiles in 248 ms natively, reaching the same fixed point (12 November 2026).
  • The Same Compiler in Clean: A typed Clean port of gen1 reaches the same fixed point natively (Clean 3.1 ARM64: 166 ms), in Clean's ABC interpreter (438 ms), and on the JMVM itself through the ABC → retag decompiler (550–574 ms, the same speed as gen1). See the performance factsheet for every route.
  • Integrated Typechecker: Sinds mid-October 2026, an integrated static typechecker (typecheck.cfp) verifies program consistency during build time.

On-the-Fly Compilation & In-Memory Dynamic Linking

JMVM provides infrastructure to compile, link, and dynamically hot-load code directly into a running VM without disk overhead:

  • Modular Compiler (saplcomp_module): Translates isolated expressions and function definitions into in-memory binary .jvb chunks (SM.chunkJvbBytes).
  • In-Memory Linker in Sapl (laadformaat/link.cfp): A complete linker written in pure Sapl (LK.lkLink). Resolves symbol offsets, jumps, and module imports entirely in RAM.
  • Dynamic Hot-Loading (@install): Using the VM primitive lookup "@install:...", newly assembled bytecode chunks are injected directly into the running VM's code and type tables.
  • Immediate Invocation (applyDynamic): Newly installed functions can be called dynamically without restarting or reloading the process.
  • Blazing-Fast REPL (repl_sapl): Boots in just ~6 ms, retains global state and evaluated CAFs across entries, and supports full session persistence (@@values/@@restore).

4. Applications: WebAssembly & Interactive Notebooks

Seamless synergy between the compiler tooling, WebAssembly, and reactive client-side notebooks.

WebSapl: 100% Client-Side WebAssembly

Thanks to the binary .jvb loading architecture, the full JMVM environment executes entirely within the browser via WebAssembly (jmvm.wasm):

  • Zero Parser Overhead in Wasm: The wasm VM build contains no textual tokenizer or parser; it consumes pre-encoded .jvb binaries directly. This minimizes binary size and accelerates startup.
  • Near-Native V8 Performance: In Chrome, the WebAssembly engine runs within about 1.47× (geometric mean; 1.2× to 2.4× per benchmark) of native bare-metal ARM64 speeds.
  • Web Worker Isolation: All execution occurs inside a dedicated Web Worker (worker.js), ensuring the browser UI never freezes during heavy evaluation or infinite stream reduction.
  • Zero Server Infrastructure: A complete compiler, linker, REPL, and virtual machine packaged as static assets; works offline or directly from local file URLs.

Interactive Reactive Notebooks (notebook.html)

The Sapl Notebook blends Jupyter-style interactive exploration with the advantages of pure lazy evaluation and incremental linking:

  • Cell-Level Incremental Compilation: When a user edits a notebook cell, only that individual cell is compiled by saplcomp_module and injected live via @install.
  • State & Heap Preservation: Global definitions, bindings, and evaluated CAFs persist in-memory across cell executions without full-document re-computation.
  • Split Compute Architecture: Intensive numeric operations can be delegated to a dedicated background compute process (:reken, server/rekenen/), maintaining UI responsiveness.
  • Functional Visualizations: Built-in integration with graphics libraries (grafisch/graphics.cfp). Lazy streams of 2D vectors and algebraic shapes are streamed directly to interactive HTML5 Canvas or SVG outputs.

Executive Summary

The JMVM ecosystem unites academic rigor (lazy graph reduction with sharing, formal retag intermediate representation) with modern systems-level performance (musttail direct threading, hardware branch prediction, in-memory JIT, and WebAssembly). The result is a robust, responsive platform for functional programming, interactive educational notebooks, and language research.
