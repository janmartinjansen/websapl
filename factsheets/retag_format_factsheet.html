Stage-4 Retag Format: The Universal Pivot

Between four functional frontends and four execution backends sits one compact, human-readable intermediate representation: Stage-4 Retag. Every frontend lowers into it, and every code generator consumes it — turning an M×N compiler problem into M + N.

1. Central Place in the Toolchain

Retag sits at the narrow waist of an hourglass architecture. Frontends resolve syntax, type classes, lambda lifting, and strictness analysis down to Retag; backends translate Retag directly into bytecode, C, or Clean ABC without duplicating any frontend logic.

2. Why Stage-4 Retag Works So Well

1. Explicit Laziness, Zero Guesswork

In a lazy language, the hardest question for a backend is “is this expression already evaluated, or must I build a thunk or force it?” Retag answers that completely before codegen: eval, thunk, and closure are all explicit AST nodes.

2. Expression-Level, Not Stack-Machine Level

Bytecode (.jmvm) and Clean’s .abc flatten functions into stack operations. Retag keeps named variables, whole functions, and structured case trees. That is why sapl2c (Retag → C) generates 2.9 MB of C and compiles gen1 in 4.1 s (248 ms self-compile, 0.34× runfast), whereas jmvm2c (bytecode → C) produced 9.3 MB of C (47 s build, 442 ms).

3. Bidirectional Bridge with Clean ABC

Retag is high-level enough to lower cleanly to Clean’s 3-stack ABC machine (sapl_naar_abc.py) and structured enough that abc2retag.py can symbolically decompile .opt.abc back into Retag — evaporating ~95% of ABC stack pushes/pops so Clean programs run on the JMVM at 0.78×–1.31× of handwritten Sapl.

4. Plain Text, Modular & Bootstrap-Safe

--emit=retag dumps the exact IR as readable text. Compiling gen1 with --emit=retag and feeding that into compile-retag produces byte-identical .jmvm/.jvb output — making it a trustworthy interface for modular linking (retaglink) and standalone backends.

3. Concrete Example: Source vs. Stage-4 Retag

Sapl Source (primes.cfp)

// Infinite stream and lazy sieve
::list = Nil | Cons !x xs

from !a  = Cons a (from (a + 1))
sieve xs = case xs (Cons a as ->
             Cons a (sieve (filter (nmz a) as)))
primes   = sieve (from 2)

Stage-4 Retag (primes.retag.txt)

// Laziness & evaluation made explicit
from !a  = Cons a (thunk (from (a + 1)))

sieve xs = case (eval(xs)) (Cons a as ->
             Cons a (thunk (sieve
               (thunk (filter (closure (nmz a)) as)))))

4. Core Constructs in Retag

Construct Meaning Backend Lowering (JMVM / sapl2c / ABC)
eval(x) Demand Weak Head Normal Form of variable x Tag check + thunk entry if unevaluated; skipped for ! strict args
eval(f x) Apply an unknown function / closure expression evalap in JMVM; closure arity dispatch in C; jsr_ap in ABC
thunk (f a b) Allocate a deferred, updatable heap computation CLOSURE node updated in-place on first evaluation
closure (f a) Allocate an unsaturated partial application (PAP) PAP / closure node capturing supplied arguments
C a b / case Strict constructor allocation and pattern match Constructor node + direct tag switch (hardware branch for tags 0/1)
f =: expr Constant Applicative Form (CAF) Zero-arity thunk evaluated at most once and cached globally
Try it yourself: run ./compile --emit=retag examples/primes.cfp to inspect the exact Stage-4 Retag output, and ./compile-retag examples/primes.retag.txt to compile it back to JMVM bytecode.
