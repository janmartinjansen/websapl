1. The Interpreter & Web Arena: JMVM vs. Clean ABC

Evaluating bytecode interpreters across native hardware execution and WebAssembly browser runtimes.

Benchmarking Methodology & Setup

All measurements were performed on an Apple M4 (Mac mini, macOS ARM64) under identical test harness conditions. Wall-clock runtime was measured across warm runs (fastest of 7 iterations for native, fastest of 5 for WebAssembly in Chrome 156 and Node 26). The benchmarks represent 12 classical functional algorithms, eval2 (the self-interpreter), and gen1 (the 7,500-line self-hosting compiler translating itself). All test variants yield 100% byte-identical output.

Key Observations: Native Interpreters

Historically, Clean's native ABC interpreter (with ~900 specialized opcodes and computed-goto dispatch) held a substantial lead over JMVM. However, following the November 2026 breakthroughs:

  • Close, but Clean's interpreter is faster: On the typed Clean programs, Clean's ABC interpreter (native abci-interpret, built with clang on the M4) needs 0.80× the time of JMVM Native (geometric mean over 13 benchmarks): it is faster on 10 of them. The JMVM is the faster interpreter on fib (246 vs. 350 ms) and level on primes. Part of the difference is the program, not the interpreter: Clean's typed code keeps numbers unboxed, where the Sapl originals run untyped.
  • Same front end: With the same Sapl programs on both interpreters (Sapl → gen1 → ABC with abcopt against Sapl → JMVM, experiments/abc_backend/) natively the ABC interpreter is a little faster: it needs 0.91× the JMVM time with abcopt (1.08× without), with all of the ABC backend's optimizations switched on (Table 1a).
  • Complex Workloads: On the 7,500-line self-hosting compiler (gen1), JMVM Native completes in 598 ms. The untyped Clean port needs 894 ms in abci (JMVM 1.49× faster); the typed Clean port needs 439 ms (abci 1.36× faster).

Key Observations: WebAssembly Execution & Fair Baselines

When deploying to the browser, the choice of comparison baseline is critical for fair assessment:

  • Fair Architectural Baseline (Locals): The stock ABC interpreter in Wasm is artificially hobbled by storing VM state in WebAssembly globals. Hoisting these to locals is a straightforward code generator fix, not an algorithmic alteration. Therefore, Clean ABC Web (+Locals) is the fairest baseline.
  • Close, not equal: Against the locals-optimized ABC interpreter (typed Clean programs, Node 26), JMVM Web needs 1.19× the time (geometric mean over the 12 benchmarks with both; JMVM Web is faster on fib, queens and parsetest, level on primes, slower on the rest, up to 2× on twice). With the same Sapl programs on both (experiments/abc_backend/, ABC with all optimizations) the two are level: ABC with locals and abcopt needs 0.96× the JMVM time (1.23× without abcopt; on gen1 0.77×), and the JMVM is 1.43× faster than the shipped stock ABC (Table 1a).
  • Wasm Slowdown Comparison: JMVM incurs a 1.58× penalty from native in Node (Chrome: 1.47×; from 1.2× on sprimes to 2.4× on fib), Clean ABC (+Locals) a 1.63× penalty and stock ABC 2.52×, each against its own native interpreter.
  • Stock Reference: Against the unoptimized stock ABC build currently shipped, JMVM Web is 1.30× faster overall (Node 26, typed Clean programs).

2. Deep Dive: Why Clean ABC Loses in WebAssembly (and How Locals Fix It)

Analyzing the V8 WebAssembly engine, state representations, and dispatch mechanics.

The Root Cause: Wasm Globals vs. Register Allocation

Why does Clean ABC lose 2.52× going to WebAssembly while JMVM loses only 1.58×? Investigation revealed that Clean's wasm generator (tools/interpretergen-wasm) stores the virtual machine's central registers—the program counter (pc), stack pointers (asp, bsp), and heap pointer (hp)—in WebAssembly global variables (global.get / global.set).

The V8 Penalty: In Chrome's V8 engine, WebAssembly globals cannot be pinned to hardware CPU registers across basic blocks or switch cases. Every single instruction executes redundant loads and stores to linear memory or memory-backed global structures, generating massive pipeline stalls.

In contrast, JMVM's C-to-Wasm build (compiled via Emscripten) maps virtual machine registers to internal function locals, allowing V8's optimizing compiler (TurboFan) to pin hot pointers directly to physical machine registers.

The Remedy: Globals $\to$ Locals Transformation

By post-processing the WebAssembly binary to hoist state pointers into function locals (only writing them back to globals when an external import is called), the ABC interpreter regains significant performance:

  • 35% Execution Time Reduction: Transforming globals to locals cuts execution time by 35% across the 12 typed Clean benchmarks in Node 26 (approx. 1.5× speedup).
  • Narrowing the Browser Gap: With locals, ABC's slowdown drops from 2.52× to 1.63× (measured again on 9 November 2026).
  • Clean vs. JMVM: With locals applied, ABC Web is still 1.19× faster than JMVM Web on the typed Clean programs (Node 26) and level on the same Sapl programs (0.96×, Table 1a). JMVM reaches its numbers out-of-the-box, without post-processing or auxiliary tooling.

3. The Native Compilers Showdown: JMVM vs. Clean Native vs. GHC Native

Pitting the interpreted JMVM against fully optimizing native ahead-of-time (AOT) compilers.

The Native Comparison Setup: Clean Native ARM64 & GHC

This comparison measures pure functional code running under native compilers against the interpreted JMVM:

  • JMVM Native: The production bytecode interpreter (runfast, musttail direct threading, superinstructions, hardware case branching on Apple M4).
  • Clean Native ARM64 (Linux in Lima VM on M4): True ahead-of-time compiled native code generated by Clean 3.1's native code generator (cg / cgarm64as.c). Because official Clean packages target Linux, this was executed inside a lightweight Lima Linux ARM64 virtual machine running on the exact same Apple M4 hardware.
  • GHC 9.14.1 Native (-O2): Glasgow Haskell Compiler native ARM64 code on Apple M4. Benchmarked using 1-to-1 Haskell ports with strictness flags (-O2 -fno-full-laziness -fno-cse) to ensure fair algorithm evaluation without artificial compile-time loop memoization.
  • sapl2c Native (12 November 2026): Sapl compiled to C with one C function per Sapl function, from gen1’s Stage-4 retag form, on the JMVM’s own memory model and GC (tagged cells, heap nodes, Cheney copying GC, also linkable against the VM’s own runtime code), built with clang -O2. Same output and allocation count as the VM on all 13 benchmarks; on average as fast as Clean native (0.99×, geometric mean of 12) and 1.16× GHC; gen1 compiles itself natively in 246 ms (the fixed point). See the sapl2c factsheet.
  • Note on jmvm2c: An experimental C-continuation generator for JMVM (jmvm2c.py via clang -O2) achieved 3,219 ms total, but because it keeps stack frames in memory, true Clean Native ARM64 (1,498 ms in the original 12-benchmark total, measured earlier) is more than 2× faster than jmvm2c, placing Clean virtually neck-and-neck with GHC.

Cross-Platform Validation: Intel Xeon x86-64 (Clean 5.1.1 Native vs. Clang 19 JMVM)

On an Intel Xeon 2.8 GHz Linux server, the Clean 5.1.1 native compiler (generating x86-64 assembly) and GHC 9.4.7 were evaluated alongside JMVM Clang 19:

  • Micro-benchmarks: On tight algebraic loops (queens, match, prolog), Clean native is 4.6×–7.2× faster than the JMVM interpreter due to unboxed register parameters on the B-stack.

4. Architectural Commentary & Analysis

Why interpreted JMVM comes remarkably close to compiled GHC native on large-scale applications.

1. Why Native AOT Wins on Micro-Benchmarks (4.4× – 6.5× over GHC on queens, match and prolog)

On small, tight recursive algorithms (such as prolog, match, and queens), GHC and Clean Native hold an expected lead:

  • Register Calling Conventions: GHC passes evaluation arguments in hardware machine registers (STG register assignment). Clean passes unboxed values directly on its native B-stack in CPU registers.
  • Interpreter Dispatch Overhead: Even with [[clang::musttail]], an interpreter must fetch the next instruction and perform an indirect branch (ldr + br). In tight loops consisting of only 2–3 arithmetic instructions, dispatch constitutes 40–50% of CPU cycles.
  • Stack Stores: Interpreters persist intermediate results to memory-backed stack frames between instructions, whereas optimizing AOT compilers keep temporary values live in registers.

2. Why the Gap Narrows to 2.0× on Real-World Code (gen1)

When scaling from toy benchmarks to real-world software—such as the 7,500-line self-hosting compiler gen1—the performance gap between the JMVM interpreter and GHC -O2 drops dramatically to just 2.0× (598 ms vs. 295 ms for the typed GHC port, 9 November 2026):

  • Memory & Cache Dominance: Real programs allocate rich algebraic data structures (ASTs, symbol tables, environments). Execution time is dominated by cache lines, pointer chasing, and heap allocations—which cost the exact same time in compiled code as in interpreted code.
  • Garbage Collection Parity: In memory-intensive workloads, both systems spend a significant percentage of time traversing and copying heap graphs. JMVM's compact Cheney copying collector and tagged cells match native GC efficiency.
  • Dispatch Amortization: Complex pattern matches and function evaluations do substantial work per instruction, diminishing the relative cost of dispatch to insignificance.
Strategic Conclusion for Educational & Web Platforms:
For client-side web development and interactive reactive notebooks, a standalone WebAssembly compiler or AOT toolchain would introduce massive complexity (compilation latency, large toolchain downloads, memory consumption) for a marginal runtime gain (typically only 1.2×–1.4× in Chrome, and virtually 1.0× in Safari). JMVM's modern interpreter architecture strikes the optimal balance: instantaneous sub-millisecond startup, incremental in-memory linking (@install), full client-side autonomy, and execution speed within 2.0× of world-class optimizing native compilers.
