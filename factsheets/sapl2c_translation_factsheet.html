How sapl2c Translates Stage-4 Retag to C

sapl2c lowers Stage-4 Retag IR into one C function per Sapl function on the JMVM’s tagged memory model and copying garbage collector. This sheet explains the translation scheme, the hard compiler problems it solves — starting with the shadow stack — and concrete examples from the generated C code.

1. Overall Translation Model

Unlike the earlier jmvm2c prototype (which translated bytecode blocks), sapl2c starts from Stage-4 Retag IR. Both the Python reference (experiments/sapl2c/sapl_naar_c.py) and the self-hosted Sapl implementation (sapl_compiler/sapl2c.cfp) emit identical C linked against a single runtime header (experiments/sapl2c/rt.h).

Aspect Mechanism in Generated C Why It Matters
Function signature static R f_name(cell* hp, cell* sp, cell a0, ..., cell a5) Uniform ABI: every tail call uses MUSTTAIL return (a single jump instruction).
Return value typedef struct { cell v; cell* hp; } R; Returns both the result value and updated heap pointer in two hardware registers.
Self tail-recursion { cell n0_ = ...; p_n = n0_; } goto top; Loops in-place without touching the C stack or reloading registers.
Tagged values (cell) 2-bit tag: integers/chars/bools unboxed (SL(n)), heap pointers aligned No stack maps needed; the GC distinguishes pointers from scalars by inspecting tag bits.

2. Problem 1: The Moving GC & The Shadow Stack

The Core Problem

The JMVM uses a copying (moving) garbage collector. Whenever a function triggers GC (during heap allocation, a CALL, or an EVALK that forces a thunk), live heap objects are moved to new addresses. However, C local variables live in CPU registers or C stack frames that the GC cannot see or rewrite.

The Solution: The VM Stack as a Shadow Stack (sp)

Any live local variable that might hold a heap pointer across a GC-capable point is spilled to sp[0..k-1] immediately before the call/GC and reloaded right after. Because every cell is self-describing (tagged), the GC simply scans sp up to the current stack pointer and updates pointers in place.

Example A: Shadow Stack in Action (f_filter from primes.c)

In filter p (Cons a as), applying p a via ap1 may allocate or trigger GC. Three live values (p_p, v2_a, v3_as) are saved on sp[0..2], the callee receives sp + 3, and the caller reloads them after CALL. Likewise, HEAPFULL(7) only spills on the slow GC path:

v3_as = PTR(p_xs)[2];
sp[0] = p_p; sp[1] = v2_a; sp[2] = v3_as;

Optimization: Non-Pointer Proofs Eliminate Spills (fib.c)

Spilling every live variable on every call would be expensive. sapl2c therefore runs a flow-sensitive non-pointer analysis with three kinds (int, non-pointer = int/char/float, and any) and a whole-program fixpoint over function return kinds. A variable proven to be a non-pointer on the current path is never spilled. 

static R f_nfib(cell* hp, cell* sp, cell p_n, cell u1_, cell u2_, cell u3_, cell u4_, cell u5_) {
  cell v1_r, v2_nfib, v3_r, v4_nfib, v5_r, v6_r;
 top: ;
  if ((LIKELY(!((p_n) & 3)) ? (p_n < SL(2)) : cmp_slow('<', p_n, SL(2)))) {
    RET(SL(1));
  } else {
    v1_r = (LIKELY(!((p_n) & 3)) ? (p_n - SL(1)) : arith_slow('-', p_n, SL(1)));
    CALL(v2_nfib, f_nfib(hp, sp + 0, v1_r, 0, 0, 0, 0, 0));
    v3_r = (LIKELY(!((p_n) & 3)) ? (p_n - SL(2)) : arith_slow('-', p_n, SL(2)));
    CALL(v4_nfib, f_nfib(hp, sp + 0, v3_r, 0, 0, 0, 0, 0));
    v5_r = (LIKELY(!((v2_nfib | v4_nfib) & 3)) ? (v2_nfib + v4_nfib) : arith_slow('+', v2_nfib, v4_nfib));
    v6_r = (LIKELY(!((v5_r) & 3)) ? (v5_r + SL(1)) : arith_slow('+', v5_r, SL(1)));
    RET(v6_r);
  }
}

Notice sp + 0 on both recursive calls: p_n and v2_nfib are proven integers, so nfib performs zero shadow-stack writes.

3. Problem 2: Laziness, Thunks & Coalesced Allocation

The Challenge

Lazy evaluation requires allocating thunk nodes, forcing them at most once via an inline tag check, and overwriting the thunk node in place (UPDATE) so subsequent demands see the result. Meanwhile, checking for heap overflow before every small node would bloat code size.

In f_take (from primes.c), sapl2c coalesces all allocations in a straight-line block into one HEAPFULL(7) check (4 words for the take thunk + 3 words for the Cons cell): 

v2_xs = p_xs;
EVALK(v2_xs, 1, {sp[0] = p_n;}, {p_n = sp[0];});
if (AUXF(*PTR(v2_xs)) == 0) {   /* Nil */
  ...
} else {   /* Cons */
  v4_x = PTR(v2_xs)[1];
  v5_xs = PTR(v2_xs)[2];
  v6_r = (LIKELY(!((p_n) & 3)) ? (p_n - SL(1)) : arith_slow('-', p_n, SL(1)));
  if (HEAPFULL(7)) { sp[0] = v4_x; sp[1] = v5_xs; GC(2); v4_x = sp[0]; v5_xs = sp[1]; }
  { cell* r_ = hp; hp += 7; CNT_CREATE(2);
    v7_thunk = TAGP(r_ + 0);
    v8_Cons = TAGP(r_ + 4);
    r_[0] = ADM_THUNK(2); r_[1] = v6_r; r_[2] = v5_xs; r_[3] = FNCELL(d_take);
    r_[4] = ADM(T_CONSTR, 5, 1, 3); r_[5] = v4_x; r_[6] = v7_thunk;
  }
  RET(v8_Cons);
}

Notice two details here: v6_r is proven int (result of - 1), so GC(2) only saves v4_x and v5_xs; and the thunk entry t_take saves self on sp, evaluates strict argument e0, calls f_take, and overwrites the thunk node in place with UPDATE(sp[-1], r.v).

4. Problem 3: Higher-Order Calls, PAPs & >6 Arguments

Functions that can appear in closures or partial applications (like nmz in filter (nmz a) as) get a FnDesc descriptor with three entry points:

  • t_nmz — thunk entry (evaluates a deferred nmz node and updates it).
  • a_nmz — apply-1 entry (completes a 1-arg partial application with one more argument).
  • s_nmz — saturated stack entry (takes arguments from sp when called dynamically or with >6 parameters).

Functions with more than 6 parameters pass arguments 0–5 in C parameters a0..a5 and any remaining arguments on the shadow stack sp, keeping the MUSTTAIL ABI uniform across the entire program.

5. Problem 4: Unboxed Fast Paths, C Call Stack & Runtime

  • Tagged arithmetic with slow fallback: LIKELY(!((x | y) & 3)) executes native integer operations directly in registers; only overloaded or non-int operands fall back to arith_slow / cmp_slow.
  • C stack & return predictor: Unlike the JMVM interpreter (which keeps its control stack in linear memory), sapl2c uses the hardware C call stack for non-tail calls. Beyond ~50 nested thunk evaluations, the CPU return-address predictor overflows (4.8 ns instead of 0.7 ns per return). This is also why sapl2c targets native silicon rather than the browser (where WebSapl’s run.wasm remains immune to JS/Wasm call-stack limits).
  • Runtime reuse: Generated C uses rt.h (matching the VM’s GC, arrays, strings, I/O, and catchable try/throw errors) or can optionally link against the VM’s own C++ runtime.
