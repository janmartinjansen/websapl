Update 9 November 2026: the optimizer is no longer part of gen1 (it made gen1's .jvb 2.1× larger); it is a separate stage behind ./compile --opt (gen1 → retagopt → retagcomp). The inline and thunkdoor passes were removed (they gained next to nothing and miscompiled gen1 without strict); the default is fold, let, params and eager, with strict as an option. Four semantic bugs were fixed (closure arguments were forced early, a <#> b reordered side effects, thunkdoor evaluated too early, try bodies were skipped) and dead-code removal was dropped (it broke programs that load functions by name, such as the REPL). The optimizer itself is about 3× faster. The tables below are the original measurements; the current numbers are in docs/2026-11-09_retag_opt_sneller_plan.md.

1. Executive Summary

Until now, the Sapl compiler pipeline translated Stage-4 intermediate ASTs (.retag.txt / .cfp_retag) directly into bytecode via Stage-5 code generation (retagcomp / stage5_codegen.cfp) without any whole-program optimizations. Because lambda lifting and lazy-tag assignment in earlier stages introduce auxiliary helper functions, non-strict wrappers, and heap thunk allocations, functional programs frequently carried significant thunk creation and evaluation overhead.

retag_opt introduces an interprocedural analysis and AST transformation pass immediately before Stage 5. It derives strict parameters across call graphs, evaluates non-cyclic let bindings eagerly, inlines small arithmetic helpers, and folds constant operations.

The real-world impact is especially pronounced on WebAssembly (WebSapl): reducing heap allocation volume saves linear memory bounds checks and register spilling in V8's TurboFan tier-2 JIT compiler, narrowing the gap between browser execution and native C++ to within 1.41× – 1.50×.

2. Pipeline Architecture

Sapl Source (.cfp) → Stage 1–3 (parse, strict, lift) → Stage 4 AST (.retag.txt) → retag_opt (Passes 1–5) → Stage 5 Codegen (retagcomp) → Native / WebSapl (.jvb)

3. The Five Optimization Passes

Pass 1Constant Folding (fold)

Performs compile-time evaluation and algebraic normalization on binary integer operations (+, -, *):

-- Associative normalization for integer constants:
(x ± c1) ± c2  ⟶  x ± (c1 ± c2)
x ± 0          ⟶  x

Eliminates nested arithmetic thunks generated by indexing and counter functions.

Pass 2Eager Arithmetic & Interprocedural HNF Analysis (eager & params)

Standard lambda lifting creates auxiliary functions like safe_1 d = eval(d) + 1 and allocates them as updateable heap thunks (thunk (safe_1 d)). Pass 2 eliminates these allocations:

  • Helper Classification (vind_goedkope_helpers): Automatically identifies functions whose bodies consist strictly of basic arithmetic on arguments or constants.
  • Interprocedural HNF Fixed Point: Iteratively computes which function parameters (f, j) and constructor fields ((C, con), k) are guaranteed to already be in Head Normal Form (evaluated) when reached.
  • Eager Inlining: If all arguments to a cheap helper thunk are known to be evaluated, the thunk allocation is eliminated entirely and replaced with direct inlined arithmetic, stripping redundant eval instructions.

Pass 3Strict Parameter Derivation (strict)

Sapl's intraprocedural strictness analyzer (strictness.cfp) historically only analyzed constructor strictness in let bindings, missing bare constructor applications like Cons !x xs.

  • Unconditional Path Analysis (altijd_eval): Inspects control-flow branches (Case, If, saturated strict calls). If a formal parameter is unconditionally evaluated along all paths, it is marked strict (!p).
  • Recursive Call-Site Forcing (_force): Unpacks call-site thunks into direct calls. Crucially, when converting Thunk(App(g, args)) into a strict call App(g, args), strict arguments of g are recursively forced, guaranteeing that no unforced closure objects are placed into strict VM stack slots.

Pass 4Unconditional Strict let Promotion (let)

Analyzes local Let expressions. When a binding let x = thunk (g args) in body is non-recursive and unconditionally evaluated across all execution branches of body (altijd_eval(x, body)), it is promoted to a strict binding: 

-- Before: allocates updateable thunk frame on heap
let x = thunk (g args) in ... x ...

-- After: evaluated directly into a local stack register without heap allocation
!x = _force(g args) in ... x ...

Pass 5Micro-Inlining & Thunk Forwarding (inline & thunkdoor)

Inlines small non-recursive functions (≤ 35 AST nodes) while strictly respecting VM invariants:

  • Case Invariant: Functions containing Case pattern-matching constructs are strictly excluded from inlining to prevent duplicating branch tables that violate Stage-5 tail-call and stack-layout conventions.
  • Thunk Forwarding: Collapses trampoline chains where a thunk merely delegates to another direct application (thunk (w a) → thunk (t a')).

Why Heap Allocation Reduction Yields Outsized Gains on WASM

In native execution (Clang -O3 with musttail direct tail-calling), allocating small 16-to-32-byte heap cells is exceptionally cheap, often hitting warm L1 CPU cache lines without stall penalties.

In WebAssembly, by contrast, heap allocation involves:

  1. Linear memory sandboxing and memory bounds checks across Emscripten's heap partition;
  2. TurboFan register spills when packing variable-arity constructors inside the VM's main dispatch loop;
  3. Indirect memory stores that compete with JIT-managed stack slots.

Eliminating 14.33 million allocations in eval saved 107 ms in native execution, but saved 180 ms in Chrome WebAssembly—a 68% larger absolute time saving on WASM.

7. Correctness & Fixed-Point Self-Compilation

The ultimate correctness test of any optimizer in the JMVM toolchain is compiler self-compilation (gen1, compiling saplcomp.cfp with itself):

  • Byte-Identical Fixpoint: When the self-compiled compiler (gen1_opt) compiles the compiler source again, the resulting bytecode is 100% byte-identical (cmp reports 0 differences) to the reference compiler.
  • Preservation of VM Invariants: Inlining strictly respects pattern-matching boundaries (excluding Case expressions), and recursive argument forcing (_force) guarantees that strict VM stack slots never receive unforced closures.

Running the Optimizer

# 1. Run standalone retag optimizer on Stage-4 AST:
python3 experiments/retag_opt/retag_opt.py input.retag.txt -o output.cfp_retag

# 2. Compile optimized AST directly to JMVM bytecode:
./compile-retag output.cfp_retag -o output.jmvm
