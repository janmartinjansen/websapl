Compiled WebAssembly Backends: Emscripten, Direct retag2wasm & Limitations

Alongside the jmvm.wasm bytecode interpreter used in WebSapl, Stage-4 Retag now lowers directly to compiled WebAssembly via two routes: sapl2c + Emscripten (AOT via C) and retag2wasm (sapl2wasm.cfp), an in-Sapl compiler emitting binary .wasm without C or Clang. Both achieve near-native speeds on shallow code, while exposing the fixed browser call stack as the primary architectural constraint.

1. Two Compiled WebAssembly Routes (vs. Interpreter Baseline)

Both compiled backends share the same Stage-4 Retag lowering — supporting Sapl, Haskell Lite, and Clean programs via abc2retag — and use WebAssembly tail calls (return_call / return_call_indirect) and multivalue returns (i64 val, i32 hp) so the heap pointer stays in Wasm registers instead of memory.

Why a 1,000-line direct generator achieves ~88% of clang -O2: Experiment B (proef_b.sh) showed that emcc -O1 (0.95×) matches -O2, and -O2 -fno-inline matches it too (1.01×), whereas -O0 is 4.49× slower and wasm-opt -O3 cannot recover that loss (4.43×). Clang’s main win is keeping named variables in Wasm locals (mem2reg/SROA) instead of linear memory. Because Stage-4 Retag already has whole functions and named locals, retag2wasm writes Wasm locals, return_call, multivalue (val, hp), and inline fast paths (EVALK, heap checks, allocation, ap1/apply_n, eq/cmp, strlen/strat/mkstr) directly — leaving GC, floats, and error cold paths in rt.wasm (60 KB).

In-Wasm Self-Compilation Chain (keten_wasm.js)

Both the Python reference (sapl_naar_wasm.py) and the Sapl compiler backend (sapl_compiler/sapl2wasm.cfp) produce byte-identical .wasm modules for all 13 standard benchmarks and for gen1 itself. 2. Browser Benchmarks (Chrome, Firefox & Safari)

Measured on Apple M4 (warm runs, best of 5; Chrome 157 and Firefox 160 headless; Safari 26.6 with screen open). On shallow programs, both compiled routes outperform jmvm.wasm by 3–4× and the Clean ABC interpreters by 3–8×. Notably, Safari 26.6 no longer penalizes direct return_call instructions (0.24× JMVM for sapl2c, matching Chrome).

3. Primary Limitation: The Browser Call Stack & Tested Solutions

Tail calls compile to return_call and consume zero stack, but every non-tail call — especially EVALK forcing a chain of thunks, strict argument evaluation, and over-saturated calls — pushes a frame onto the host WebAssembly engine’s call stack. Natively, sapl2c runs on a 4 GB thread stack; jmvm.wasm keeps its call stack in linear memory. In browsers, the Wasm stack is capped around ~1 MB and cannot be enlarged from web pages (nor via Web Workers, which actually have smaller stacks in Chrome and Safari: 9/14 fail in Chrome workers vs. 6/14 on main thread; 11/14 fail in Safari workers vs. 3/14 on main thread).

Option A • R2W_SEG

JSPI Stack Segments

Checks a global depth counter on non-tail calls; past depth 2,000, suspends via WebAssembly.Suspending onto a fresh WebAssembly.promising stack.

  • Pros: Keeps normal functions intact; runs all 14 in Chrome & Firefox.
  • Cons: Counter adds ~23% overhead to every program; segment switches cost ~0.3 ms in Firefox (gen1 slows to 4.7 s); absent in Safari 26.6.
Option B • R2W_CPS

Own Stack (Continuation Form)

Saves live variables and a continuation index onto the shadow stack (sp) in linear memory and jumps with return_call / return_call_indirect.

  • Pros: Works in all browsers (no JSPI needed); in Node/Chrome averages 1.00–1.12× direct (twice & primes get faster!).
  • Cons: ~2× slower in Firefox; 4–13× slower in Safari (1.38× slower than JMVM) due to 8-arg return_call_indirect in JSC.
Recommended • Hybrid

Tiered Execution

Run Tier 0 (fast direct Wasm, zero counter) by default; catch overflow traps early (twice 0.5 ms, sort ~50 ms, gen1 ~155 ms) and restart on Tier 1:

  • Chrome & Firefox: restart on R2W_CPS (~1.50× / ~2.56× native est. across all 14).
  • Safari: restart on jmvm.wasm (~1.87× native est. across all 14).

4. Other Limitations & Open Engineering Items

Language & Compiler Gaps in retag2wasm

  • Not yet implemented: try/catch (setjmp) halts with an error in both sapl_naar_wasm.py and sapl2wasm.cfp; float literals are not yet parsed to IEEE-754 bits in sapl2wasm.cfp.
  • CPS/JSPI variants in Python only: R2W_CPS and R2W_SEG currently live behind flags in sapl_naar_wasm.py and are not yet ported to sapl2wasm.cfp.
  • Generator throughput: running inside jmvm.wasm, sapl2wasm currently takes ~2.7× as long as gen1 itself (1,012 ms vs. 376 ms for gen1) because it re-parses C-expression strings and builds bytes via append.
  • WebSapl worker integration: the end-to-end Wasm chain runs via keten_wasm.js in Node, but is not yet wired into WebSapl’s browser notebook worker UI.

Browser & Deployment Constraints

  • Restartability requirement: Tier-0 → Tier-1 fallback requires buffering stdout/DOM effects until completion; programs consuming interactive input mid-run cannot transparently restart after an overflow trap.
  • Asyncify ruled out: Binaryen’s wasm-opt --asyncify inflates fib by 3.4× (18.8 KB → 63 KB) and instruments every call path.
  • No page-level stack control: Only Node/V8 (--stack-size) or a self-managed desktop Chromium/Electron shell (--js-flags) can raise the engine stack directly.
  • 32-bit Wasm & threads: wasm32 memory limits apply (tighter on mobile/iOS Safari), and SharedArrayBuffer threads require COOP/COEP HTTP headers.
