Compiled WebAssembly Backends: Emscripten, Direct retag2wasm & Limitations

Alongside the jmvm.wasm bytecode interpreter used in WebSapl, Stage-4 Retag now lowers directly to compiled WebAssembly via two routes: sapl2c + Emscripten (AOT via C) and retag2wasm (sapl2wasm.cfp), an in-Sapl compiler emitting binary .wasm without C or Clang. Both achieve near-native speeds on shallow code, while exposing the fixed browser call stack as the primary architectural constraint.

Update 25 November: the whole chain now runs in the browser on the demo page sapl2wasm.html, which shows the JMVM, direct retag2wasm and retag2wasm with its own stack side by side. Safari’s slowness with the own stack turned out to be the tail call itself: in JavaScriptCore every return_call costs ~7× an ordinary call. A trampoline variant fixes that, and the page picks it automatically for Safari and iOS (see section 3).

1. Two Compiled WebAssembly Routes (vs. Interpreter Baseline)

Both compiled backends share the same Stage-4 Retag lowering — supporting Sapl, Haskell Lite, and Clean programs via abc2retag — and use WebAssembly tail calls (return_call / return_call_indirect) and multivalue returns (i64 val, i32 hp) so the heap pointer stays in Wasm registers instead of memory.

Four Tries at WebAssembly (Why Retag Was the Turning Point)

A compiler over a fast interpreter only pays off around ~3×. Both earlier bytecode-level attempts stayed well below that threshold (1.5× in wasm, 1.3× in jmvm2c) because bytecode still acts like a stack machine; starting from Stage-4 Retag lets variables become Wasm locals and unlocked 3–4×:

Why a 1,000-line direct generator achieves ~88% of clang -O2: Experiment B (proef_b.sh) showed that emcc -O1 (0.95×) matches -O2, and -O2 -fno-inline matches it too (1.01×), whereas -O0 is 4.49× slower and wasm-opt -O3 cannot recover that loss (4.43×). Clang’s main win is keeping named variables in Wasm locals (mem2reg/SROA) instead of linear memory. Because Stage-4 Retag already has whole functions and named locals, retag2wasm writes Wasm locals, return_call, multivalue (val, hp), and inline fast paths (EVALK, heap checks, allocation, ap1/apply_n, eq/cmp, strlen/strat/mkstr) directly — leaving GC, floats, and error cold paths in rt.wasm (60 KB).

In-Wasm Self-Compilation Chain (keten_wasm.js)

  • no clang on the server, and compiling inside the process (retag2wasm is itself wasm);
  • the module as a sandbox.

Cold Start & Browser Memory

  • Cold first run (module already compiled): fib finishes in 150–220 ms in Chrome/Firefox/Safari, vs. ~1.3 s for jmvm.wasm and 1.3–2.9 s for ABC interpreters (no interpreter loop to warm up).
  • Memory footprint: sapl2c-wasm uses 73–134 MB (gen1 307 MB), vs. ~690 MB for jmvm.wasm and 320 MB for ABC.

3. Primary Limitation: The Browser Call Stack & Tested Solutions

Tail calls compile to return_call and consume zero stack, but every non-tail call — especially EVALK forcing a chain of thunks, strict argument evaluation, and over-saturated calls — pushes a frame onto the host WebAssembly engine’s call stack. Natively, sapl2c runs on a 4 GB thread stack; jmvm.wasm keeps its call stack in linear memory. In browsers, the Wasm stack is capped around ~1 MB and cannot be enlarged from web pages (nor via Web Workers, which actually have smaller stacks in Chrome and Safari: 9/14 fail in Chrome workers vs. 6/14 on main thread; 11/14 fail in Safari workers vs. 3/14 on main thread).

Option A • R2W_SEG

JSPI Stack Segments

Checks a global depth counter on non-tail calls; past depth 2,000, suspends via WebAssembly.Suspending onto a fresh WebAssembly.promising stack.

  • Pros: Keeps normal functions intact; runs all 14 in Chrome & Firefox.
  • Cons: Counter adds ~23% overhead to every program; segment switches cost ~0.3 ms in Firefox (gen1 slows to 4.7 s); absent in Safari 26.6.
Option B • R2W_CPS

Own Stack (Continuation Form)

Saves live variables and a continuation index onto the shadow stack (sp) in linear memory and jumps with return_call / return_call_indirect.

  • Pros: Works in all browsers (no JSPI needed); in Node/Chrome averages 1.00–1.12× direct (twice & primes get faster!).
  • Cons: ~2× slower in Firefox; 4–13× slower in Safari (1.38× slower than JMVM).
  • Why Safari (measured 25 Nov): not the 8 arguments or the indirection. In JavaScriptCore every tail call costs ~3.4 ns, against 0.5 ns for an ordinary call (Chrome 0.23–0.40 ns, Firefox 1.4–1.6 ns; experiments/sapl2c/wasm/r2w/safari_micro/).
Option B′ • for Safari • built 25 Nov

Own Stack as a Trampoline

The same continuation form without tail calls: every function returns the next state and table index, and a loop in sapl_start calls it (in chunks of 1,000, so V8 still tiers the loop up). Generated by sapl2wasm.cfp for a *.t.wasm target, byte-identical to the Python reference.

  • Safari: ~2× faster than the tail-call form, and now 1.4–3.2× faster than the JMVM on all 13 benchmarks (was 0.7–1.7×).
  • Chrome & Firefox: 3–7× resp. ~2.8× slower than tail calls, so those keep the tail-call form.
  • Demo: sapl2wasm.html picks the trampoline automatically for JavaScriptCore (Safari and every browser on iPhone/iPad); a “Calls via” menu (or ?eigen=tail|tramp) overrides it to show the effect.
Recommended • Hybrid

Tiered Execution

Run Tier 0 (fast direct Wasm, zero counter) by default; catch overflow traps early (twice 0.5 ms, sort ~50 ms, gen1 ~155 ms) and restart on Tier 1:

  • Chrome & Firefox: restart on R2W_CPS (~1.50× / ~2.56× native est. across all 14).
  • Safari: restart on the trampoline own stack (0.48× JMVM on the 13 benchmarks); before 25 Nov the fallback was jmvm.wasm.

4. Other Limitations & Open Engineering Items

Language & Compiler Gaps in retag2wasm

  • Not yet implemented: try/catch (setjmp) halts with an error in both sapl_naar_wasm.py and sapl2wasm.cfp; float literals are not yet parsed to IEEE-754 bits in sapl2wasm.cfp.
  • JSPI variant in Python only: the own stack (*.k.wasm, 24 Nov) and its trampoline (*.t.wasm, 25 Nov) are in sapl2wasm.cfp; R2W_SEG still lives only behind a flag in sapl_naar_wasm.py.
  • Generator throughput: running inside jmvm.wasm, sapl2wasm currently takes ~2.7× as long as gen1 itself (1,012 ms vs. 376 ms for gen1) because it re-parses C-expression strings and builds bytes via append.
  • WebSapl integration: the chain runs in the WebSapl worker (COMPILE_WASM) and on the demo page sapl2wasm.html (24–25 Nov), but not yet in the notebook.

Browser & Deployment Constraints

  • Restartability requirement: Tier-0 → Tier-1 fallback requires buffering stdout/DOM effects until completion; programs consuming interactive input mid-run cannot transparently restart after an overflow trap.
  • Asyncify ruled out: Binaryen’s wasm-opt --asyncify inflates fib by 3.4× (18.8 KB → 63 KB) and instruments every call path.
  • No page-level stack control: Only Node/V8 (--stack-size) or a self-managed desktop Chromium/Electron shell (--js-flags) can raise the engine stack directly.
  • 32-bit Wasm & threads: wasm32 memory limits apply (tighter on mobile/iOS Safari), and SharedArrayBuffer threads require COOP/COEP HTTP headers.

5. What This Means for Clean, iTasks & Deployment Choices

Implications for Clean & iTasks

  • Client speed & one portable target: 3–8× faster than the ABC interpreter with no warm-up and less memory; server and browser share the same Retag pipeline instead of per-platform cg + assembly runtimes.
  • Graph exchange without binary compatibility: pack/unpack serializes thunks, closures, sharing, and cycles by name (not address layout), and uniqueness is already checked by the Clean front end so arrays update in place.
  • Work needed for real iTasks apps: add pack/unpack and ccall support in sapl2c; module-based code shipping (ABC streams functions on demand, Wasm loads modules); JS interop (JSVal, callbacks); 64-bit Real, 62/64-bit Int + bit ops; and boxed arrays / dynamics via abc2retag.

Deployment Questions (Which Tiers to Build First)

  • 1. Which devices? Desktop only, or iPads too? On iOS every browser runs WebKit, so Safari performance and stack fallback matter immediately (the trampoline is the answer for now; not yet measured on a real iPad).
  • 2. One prescribed browser? If clients can require Chrome/V8, the explicit stack (R2W_CPS) has near-zero average overhead, runs every program, and avoids Tier-0 → Tier-1 restarts.
  • 3. A desktop app? Inside a self-managed Chromium shell (Electron), V8’s stack limit can be raised directly via --js-flags, eliminating the stack obstacle altogether.
  • 4. Where is an interpreter not enough? Most iTasks clients are likely fast enough on jmvm.wasm / ABC; compiled Wasm targets compute-heavy client paths.
